## 0. 前提と結論

指揮官の決定（2026-10-17、Issue 本文＋追加の制約）:

1. Stage を主画面にし、今のチャット画面はサブ（`/chat`）に下げる。
2. **左には既存のサイドメニュー（シェル）がある。** Stage はメニューの右の**コンテンツ領域**に入る
   （1300px の画面ではメニュー 232px を引いた **1068px**、メニューを畳むと 1244px）。
3. **入力欄はテキストウィンドウの中。**（変えない）
4. チャットの細かいステータス（ターンリボン・ツールカードの詳細・トークン/キャッシュ等）は主画面に持ち込まない。
   状態はキャラの表情・モーション・ガジェット・ネオンで伝え、数値とログは生ビュー（Tab）・デバッグ（D）・
   サブのチャット画面に任せる（§3）。
5. ホワイトボードは **「横からスライド」か「スクリーンが上から下りてくる」のどちらか一方**だけ実装する（§2）。
6. ボード表示中は**キャラが画面の右端に寄り**、後ろのボードが見やすい構図にする。寄る/戻るは
   **キャラ層のオフセット**で表す（背景は動かしすぎない、キャラ層とボード層は分離。§4）。

結論:

- **ボードは「スクリーンが上から下りてくる」を推奨**（理由は §2.3。読みやすさは同等、キャラとの共存・
  スマホ・ジェスチャ衝突で勝ち、実装量の差は CSS 10 行程度）。
- 構図は 1 案に絞った: 下にテキストウィンドウ 1 枚（名前札・聞いた言葉 1 行・台詞・入力欄）、上はシーン。
  ボード表示中はキャラが右端へ寄り、ボードは左（メニュー側）から幅 約 680px を使う。

## 2. 構図とホワイトボード

### 2.1 構図（1 案）

| 要素 | 1300px（コンテンツ 1068×860） | 390px（DPR 2） |
|---|---|---|
| サイドメニュー | 既存のシェルそのまま（左 232px） | 既存の上部バー（☰）＋ドロワー |
| シーン | 拡大率 ×3、キャラ中央。背景とキャラは別レイヤー | ×1.5（端末 3px/ドット）、上部 |
| テキストウィンドウ | 下部 左右 24px。名前札・聞いた言葉 1 行・台詞・入力欄・ヒント・「ログ」「生ビュー」 | 下部。ヒントは省略 |
| 承認の選択肢 | テキストウィンドウの右上（アンバー） | テキストウィンドウの上、全幅 |
| バックログ | テキストウィンドウの上に重なる（↑ / 「ログ」）。シーンは暗くする | 上部いっぱい |
| ボード | 左 24px〜（幅 約 680px）、天井〜テキストウィンドウの上。キャラは右端へ | 全幅−56px。キャラは右端から顔をのぞかせる |

モックは 9 状態（a 待機 / b 入力中（IME） / c タイプ中 / d ボード / e バックログ / f 承認 / g スマホの
キーボード表示中 / h 送信直後（停止） / w ブレーカー WARNING）× 2 方式 × 1300・390px。
シェルは本物の `tokens.css`・`components.css` とマークアップで描き、背景とキャラはデモから別々に撮った
2 レイヤー（`tools/capture_layers.cjs`）を重ねている。

### 2.2 2 方式

- **横スライド**（`mock-slide.html`）: 枠付きの立て看板型ボードが、コンテンツ領域の左端（メニュー側）から
  右へ滑り込む。`transform: translateX()` 1 本。
- **スクリーン下降**（`mock-screen.html`）: 天井のケース（ハウジング）が出て、スクリーン布が下へ巻き下りる。
  布は `clip-path: inset(0 0 (1−e)×100% 0)`、下端のウェイトバーが同じ進み具合で下がる。

どちらも同じ時間（約 270ms、ease-out、16 フレーム）で、**同じ進み具合でキャラ層が右へ動く**（§4）。
遷移は `anim/board-<方式>-<幅>.mp4` と 6 コマのシート `anim/board-<方式>-<幅>-frames.png`。

### 2.3 比較と推奨

| 観点 | 横スライド | スクリーン下降 |
|---|---|---|
| コード・表の幅と読みやすさ | 幅は同じ（1300px で 約 680px、390px で 328px）。枠とトレイで高さ −20px | 同じ幅。天井から使えるので高さ +20px。布の地は明るくコードは暗いブロック（コントラスト §9） |
| キャラとの共存 | ボードもキャラも右へ動く（同じ向き）ので「押し出される」ように見える。メニューの端から出てくるため、メニューのパネルが開いたようにも読める | ボードは縦、キャラは横に動くので動きがぶつからない。天井から下りる部屋の道具として読め、「キャラが脇へ退いてスクリーンを見せる」構図になる |
| スマホでの変換しやすさ | 左からのドロワー（シェルのメニュー）と同じ向きで、iOS の左端スワイプ（戻る）とも重なる。閉じる操作（左スワイプ）があいまい | 上部バーの下から下りる。閉じるは上スワイプ / ×。ジェスチャの衝突なし |
| アニメーションの実装量 | CSS 1 行（transform。枠は共通） | CSS 約 10 行（ケース・布・ウェイトの 3 要素、clip-path）。JS は同じ（進み具合 1 つ） |
| reduced-motion | 即時表示 | 即時表示 |

**推奨: スクリーン下降。** 読みやすさは同等で、キャラとの共存とスマホで明確に勝ち、余計な実装は CSS 10 行程度。
横スライドを選ぶ理由が残るのは「メニュー側から出る」ことを一体感として好む場合だけ。

## 3. 主画面に残す最小限の情報

**残すもの**（これ以外は出さない）:

1. テキストウィンドウ: 名前札、聞いた言葉（自分の送った文の 1 行）、台詞、入力欄、画像添付（チップ）、
   **送信 / ■ 停止**（ターン実行中は送信ボタンが停止になる）、送れない理由の 1 行（承認待ち・処理中・未接続）、
   結果が分からないまま切れた送信の **「同じ内容を再送 / 破棄」**（二重送信を防ぐ安全装置なので残す）。
2. **承認の選択肢**（アンバー）と「引数を見る（マスク済み）」パネル（既存の Stage と同じ）。
3. **ブレーカー**: ネオンの色（既存）と定型文 1 文（`stage.say_warning` 等）。デスクトップはサイドメニューの
   既存チップ（ブレーカー / 保留中の承認 / 接続）がそのまま受け持つ。スマホはメニューが隠れるので、
   **正常でない間だけ**シーン右上に小さなチップを 1 つ出す（「⚠ ブレーカー WARNING」「承認待ち 1」）。
4. 接続断: 定型文（`stage.say_offline`）と送信不可。
5. ボタンは「ログ」（↑）と「生ビュー」（Tab）の 2 つだけ。デバッグは D キーのみ。

**持ち込まないもの** → 生ビュー（Tab）/ デバッグ（D）/ チャット / 観測へ:
ターンリボン、ツールカードの詳細、トークン・キャッシュ・コスト、Neural State の数値、ブレーカーの数値と履歴、
承認の待ち行列、モデル名、即断（sokudan）判定、イベントの通し番号。

状態は**キャラの表情・モーション（#351）・ガジェット・ネオン**で伝える（既存の Stage の規則のまま）。

## 4. キャラ層のオフセット（右端へ寄る / 戻る）の実現方針

今の描画は 1 キャンバスだが、レイヤーは既に `room` 群と `char` 群に分かれ、位置は `layerOffset()` で決まる
（CRITICAL の揺れがキャラと手前の小物だけを動かす仕組み、#346）。これを使う:

1. **入力 1 つ**: `aside`（0〜1）。ボードを開くと 0→1、閉じると 1→0（約 270ms、ease-out）。UI のイベントなので
   room.js の「部屋が動いてよいのはイベント・視差・環境アニメだけ」の規則に収まる。
2. **キャラ層**: `char` 群（本体・髪・持っている小物、深度 ≥ 1）に `round(aside × ASIDE_X)` ドットを足す。
   ASIDE_X はキャラの顔がコンテンツ右端から 120px（1300px）/ 10px（390px）に来る量を、表示幅から決める
   （1300px で 約 140 ドット）。整数ドットに丸めるのは今の `layerOffset` と同じ。
3. **背景**: `roomFrame().cam` を `aside × 12` ドット（390px は 8）だけ動かす。深度で掛かるので、奥のレイヤーほど
   動かない。12 ドット＝1300px で 36px。
4. **ボード層をキャラの後ろに挟む**: ボードは DOM（選択・コピー・読み上げのため）なので、キャンバスを
   **2 枚**にする — 奥: `room` 群（前景の植物も含む）、手前: `char` 群（透明背景、`alpha: true`）。
   重なり順は「部屋 < ボード < キャラ < テキストウィンドウ」。テクスチャは群ごとに別なので二重読み込みはない。
   グレーディング（dim / desat / ambient）は各レイヤーのシェーダが持つので、同じフレームの値を両方へ渡す。
5. **ボードの幅**: キャラ層の左端（テキストウィンドウより上の行で、顔の中心から 75 ドット左。キャラ層で実測）から
   16px 手前まで。1300px で 約 680px。コードの長い行はブロック内で横スクロール。
6. **スマホの例外**: 390px ではボードがキャラの体を避けられないので、**ボードがキャラより手前**に出て、
   キャラは右端 56px の帯から顔をのぞかせる。
7. **視線**: ボード表示中は `gaze` を左（ボード側）へ。#351 の視線トラックで足りる（新しい目の差分は不要か、
   モーション担当と確認）。
8. 検証: 2 キャンバスの合成が 1 キャンバスの今の絵と一致すること（`aside = 0` で画素比較）、`aside` の
   各値でキャラ層が整数ドットで動くこと。

**実装（フェーズ2）**: 描画は 1 つの WebGL コンテキストのまま、three.js のレンダーレイヤーで 2 回描く。キャラ群
（本体・髪・マグの湯気・きらめき・深度 1 以上のガジェット）をレイヤー 1 に置き、ボードが出ている間だけ
(1) 部屋の回を描いて奥の 2D キャンバス（`#view-room`）へ `drawImage` で写し、(2) キャラ群の回を透明な手前の
キャンバス（`#view`、`alpha: true`）に描く。キャラ群の加算光（ノートPCの画面光など）は「描画先のアルファを
変えない」ブレンドにして、透明の上でも 1 回描きと同じ加算になる（色の式は AdditiveBlending と同じ）。ボードが
閉じている間は今までどおり 1 回描き。`?split=1`（検証用）で常に 2 回描きにして 1 回描きと比べると、1300px・
390px とも**画素が完全に一致**（差分 0 画素、`aside = 0`）。`aside` は `roomFrame()` の 5 番目の入力（UI の
進み具合。キャラのチャンネルではない）で、`cam`（部屋のパン、深度倍）と `aside`（深度 1 以上だけ）になる。
背景のバンドと前景（`fore`）は `aside` を受けない。ボードの中身は部屋の入力に一切入らない（テスト）。
前景（`fore`、ふだんはキャラの手前）は奥のキャンバスに入るので、ボード表示中だけキャラの後ろになる。
ボードの幅は実機で見直した: 顔の中心から 75 ドット左（頭の高さで測った値）ではテキストウィンドウ近くのコートの
下にボードの右下が隠れたので、92 ドット左までにした（1300px で 約 632px、フェーズ0 のモックの絵と同じ幅）。
キャラの移動量（約 140 ドット）は設計どおり。幅が 360px 未満になる横長の狭い画面ではスマホと同じ「手前」になる。

モックはこの方針の見た目（背景 12 ドットのパン＋キャラ層の移動）を、2 レイヤーの静止画で再現している。

## 5. ホワイトボードの出し分け（決定的な判定）

### 5.1 規則

返答テキストを Markdown 部分集合で解析し、次の**どれか1つでも**当たれば「ボード」、どれも当たらなければ「台詞」。

1. コードブロック（``` / ~~~。閉じていなくても）がある
2. 表（GFM: ヘッダ行+区切り行）がある
3. 見出し（`#`〜`######`）がある
4. 箇条書き・番号付きリストの項目が **3 個以上**
5. 引用（`>`）がある
6. 見える文字数（Markdown 記号を除く）が **140 字超**
7. 段落が **3 個超**（台詞は 1 段落=1 ページ、最大 3 ページ）
8. 1 段落の中の改行が **4 行超**

- ボードのとき、**最初の段落が 120 字以下の普通の段落なら「リード」として台詞で話し**、ボードには残りを出す。
  リードが無い返答は定型文（「ボードに書きました。」）を話す。
- 閾値は表示上の定数で、モデルの出力や会話の内容から学習・変化させない。
- ストリーム中は「台詞→ボード」だけ（降格しない、0.25 秒ごとに再判定）。**返答が終わったら全文を一括で判定し直す**
  （ログ・再読込と同じ答え）。それが台詞ならこの返答で下ろしたボードを巻き上げる（ピン留め中は残す）。
- 計算量と描画量の上限（全経路: ボード・ログ・ストリーム）: 先頭 64 KiB、行は手書きの走査（バックトラックする
  正規表現なし、各ステップで必ず 1 行以上進む）、ブロック 2,000、表は 24 列 × 400 行、描画 20,000 要素（ログは
  1 返答 3,000）。超えた分は「省略」の注記。計測: 修正前に 5 秒かかった病的入力（```＋長い言語名、`[` の連続）が
  10 ms 以下（`tests/stage_board_test.cjs`、4 倍の入力で 8 倍未満の時間）。
- 実装: `dashboard/stage/js/markdown.js`（`classify` / `classifyStream`、`LIMITS`）。台詞のときは Markdown の
  記号を除いた文字（`**大事**` → 「大事」）を話す。リードは「最初の段落が 4 行以下・120 字以下・インライン
  コードなし」。判定は返答の先頭 64 KiB（UTF-8、文字を割らない）で行い、超えた分はボードに「全文はチャット画面で」。

### 5.2 試行（`tools/md_subset.mjs` + `classify_trial.mjs`）

| ケース | 種別 | 判定 | 理由 |
|---|---|---|---|
| CSV 平均の関数（コード3・表1） | 実測 | ボード | code×3, table×1, heading×4, 1716 字。リード=最初の段落 |
| 「一言ちょうだい」への返答 | 実測 | 台詞 | 101 字・2 ページ |
| 挨拶 / URL 1 つ / インラインコード | 合成 | 台詞 | — |
| 箇条書き 2 個 | 合成 | 台詞 | — |
| 箇条書き 3 個 | 合成 | ボード | list items 3 |
| 153 字の地の文 | 合成 | ボード | chars 153 > 140 |
| 4 段落 / 5 行 | 合成 | ボード | paragraphs 4 > 3 / rows 5 > 4 |
| max_tokens で止まった旨のエラー文 | 合成 | 台詞 | — |
| 生 HTML（`<img onerror>`） | 合成 | 台詞（**文字のまま**） | — |
| 見出しのみ / 引用 / 閉じないコード | 合成 | ボード | heading / quote / code |

ハイライタは実測返答の Python で `kw/fn/type/str/com/num/punc` に分け、連結すると元のコードに一致（往復一致）。

### 5.3 ボードの操作と複数ブロック

- 1 返答 = 1 枚。中のコード・表・見出しは縦に並べ、フッタに「見出し 4・コード 3・表 1」とページ点。
- **閉じる**（×・Esc・スマホは上スワイプ）/ **ピン留め**（次の返答が来ても差し替えない。新しいボードはバックログの
  「▶ 開く」から）/ **コピー**（ボード全体の Markdown 原文。各コードブロックにも個別のコピー）。
- ピン留めしていなければ次のボード返答で中身だけ差し替える（下ろし直さない）。閉じるとキャラは中央へ戻る。
- 過去のボードはバックログから開き直せる（直近 50 ターン = 既存 `/api/chat/history` の範囲）。
- 64 KiB を超える返答は先頭だけを出し、「全文はチャット画面で」と出す。

- **目標グラント（W5b, #296）** — ゲートウェイ `autonomy.stage_c` がオンのときだけ、稼働状況モードに
  目標グラントの欄が出る（状態・目標の状態・反復 n / 最大と実行中か・残り時間と残り予算のメーター・
  最後の終わり方・直近 5 反復・承認待ち / あなたの確認待ちの案内）。表示だけで、操作は設定 → 目標グラント。
  承認カードの中身・目標の文・引数は出さない。オフなら何も変わらない（`/api/activity` も DOM も以前と同じ）。
  実行部（`autonomy.stage_c_exec`）がオンのとき、反復が始まったらボードが閉じていれば稼働状況で下りてくる
  （返答・ピン留め・本人のターン・ログ表示中・タブ非表示なら下りない）。判定表は docs/stage.md。
  W6c 以降、完了の申告があればハーネスが測った証跡（チェック・作業ツリー・進捗・申告時のトークンと残り時間）と
  「まだあなたを待っています」を出し、W6d のハートビート開始が有効なグラントでは開始の回数・見送りの理由・
  最後のハートビート反復のトークンと時間を行で出す（どちらも表示だけ）。アルファ版。概要と既知の制約は
  [autonomy_ja.md](autonomy_ja.md)、ボードの仕様と判定表は [stage.md](stage.md#the-goal-grant-on-the-board-adr-0011-stage-c-w5b-of-296)。

## 6. 安全

## 11. `/new`（新しい会話）— フェーズ3で実装（`POST /api/chat/session/new`）

**実測（チャットサーバー・偽モデル、2026-10-17）**: 会話の文脈は**サーバープロセスの寿命**で区切られる。

| 確かめたこと | 結果 |
|---|---|
| 同じプロセスで 2 回送信 | モデルに渡るメッセージが 1 → 3（前のターンを引き継ぐ） |
| サーバーを再起動して送信 | モデルに渡るメッセージは 1（文脈は引き継がない）。`/api/chat/history` は 0 件に戻る |
| 再起動で残るもの | `neural-state.json`（6 次元の値）、エピソード記憶（3 件のまま）、`turns.db`（`/api/turns`）、承認ストア |
| 会話をリセットする HTTP ルート（フェーズ2時点） | 無かった（チャットサーバーは `session_manager` を使わず、会話は `NXPAgent.agent.messages` のメモリ上だけ） |

**フェーズ3で入れたもの（指揮官承認済み）**: `POST /api/chat/session/new`。再起動と同じ効果を、会話だけに与える。

1. **効果**（`NXPAgent.start_new_conversation`）: SDK の Agent（毎ターン作り直すもの）、チェックポイントから
   復元した `_restored_messages`、エンジンが持つ履歴のコピー（`engine.conversation_history`）、この会話の
   プロンプト計測（`last_prompt_cache` など）と `SoulCompactionGuard`（会話の大きさを追う。再起動後と同じ新品）を
   捨てる。チャット API の履歴（`/api/chat/history`）とセッション累計トークンも空にし、履歴に
   `session: { id, started_at, reason: "new", cleared, request }` を返す（画面はこれで境界線を出す。`request` は
   そのセッションを始めた `Idempotency-Key` の SHA-256 先頭 32 桁。キーそのものは出さない）。履歴の GET は
   ターンと session を同じロック区間で取る（リセットの途中の「旧ターン＋新 session」は返らない）。
   **変えないもの**: Neural State（値も減衰の時刻も）、ブレーカー（レベル・ヒステリシス・クールダウンの
   ターン数。新しい会話でブレーカーは下がらない）、記憶（エピソード・意味・手続き）、SOUL・アイデンティティ、
   承認（保留中・履歴）と操作台帳、ディスク上のチェックポイント、スケジューラ、ツールのルール、`turns.db`。
2. **フェイルクローズ**: ターン実行中（ストリーム中・Webhook・承認の再開中を含む。すべて同じ turn lock）→ 409
   `turn_running`。承認待ち（ライブ・再起動で復元したもの）→ 409 `approval_pending`。承認済みで再開が
   lock 待ち → 409 `resume_pending`（再開はチェックポイントの**古い会話**を戻すので）。承認の判断が処理中 →
   最大 5 秒待って 409 `decision_in_progress`。承認状態が読めない → 503 `approvals_unavailable`、監査ログ
   （events.db のハッシュ連鎖）が書けない → 503 `audit_unavailable`。いずれも何も変えない。
   **判断とリセットは排他、待ちはすべて有限**（レビュー対応）: 承認ブローカーは判断のあいだ（ストアの承認済みへの
   遷移から再開の予約まで）共有の再入可能ロックを持ち、再開の予約もそのロックを取る。リセットはその中で「判定 →
   リセット」だけを行う。取得はどこでも上限つき（`timed_lock`、5 秒）: 判断が取れなければ 503 `busy`（**記録しない**。
   承認待ちのまま、押し直せば判断される。`busy` になるのは**取得の失敗だけ**で、取得後の `_decide()` から出た例外は
   そのまま伝わる＝記録後の失敗を「記録していない」と言わない。503 では冪等キーが消費されないので、承認カードは残り、
   同じキーの押し直しは 1 回だけ記録される）、リセットが取れなければ 409 `decision_in_progress`、再開の予約が取れ
   なければその承認は再開を拒否して失効させる（見えないまま古い会話を戻すことはしない）。先に始まった判断・予約が
   あればリセットは拒否、リセット中に来た予約は待たされ、その後のリセットは `resume_pending`。判断が後に来る場合は、
   承認待ちがあった時点でリセットは拒否済み（承認待ちが無ければ判断する対象が無い）。
   **ロックの順序**（コードから。逆順の取得は無い）:
   - `/new`: turn lock（`generation_lock` はチャットサーバーの `turn_lock` そのもの、非ブロッキング）→（監査の
     `session.reset` 行。共有ロックの外、event store の内部ロック）→ 共有ロック（上限 5 秒）→ broker の
     condition（`pending()`）・`state_lock` → 共有ロックを外す →（結果の監査行）→ turn lock を外す。
   - 承認の判断: 共有ロック（上限 5 秒）→ `_decide()`（broker の condition、承認ストア）→ 再開の予約（同じ
     共有ロック、再入）→ 再開スレッドの起動（起動するだけで待たない）→ 共有ロックを外す。turn lock は取らない。
   - 再開スレッド: turn lock（上限 300 秒、既存）→ 再開 → turn lock を外す → `resume_finished()`（共有ロック、
     上限 5 秒で取り直す）。共有ロックを持ったまま turn lock は取らない。
   - 共有ロックの中で行うのは承認ストアの読み書き（SQLite、既定の busy timeout 5 秒。通常は数 ms）と
     会話のリセット（`NXPAgent.start_new_conversation` の代入数個と履歴の `clear()`、O(1)〜O(50)、µs 単位）だけ。
     event store（監査）はこの中では使わない。
   テスト: `tests/test_new_session_locks.py`（監査の書込みを止めても共有ロックは空いていて判断は 2 秒以内に 202、
   共有ロックを塞ぐと判断は上限内に 503 `busy` で承認待ちのまま・解放後に判断できる、予約は上限で `LockBusy`、
   実際の経路を走らせてロックの取得順を記録し、どの 2 つも両方向に取られないこと・共有ロックの中で event store も
   turn lock も取られないこと）、`tests/test_new_session_concurrency.py`（ストアの遷移直後で判断を止めた状態での
   リセット → 409、予約がリセットを待つこと、ブローカーが判断中にロックを持つこと）。
   同一オリジン・CSRF は `install_security`。`Idempotency-Key` は**必須**（無い・128 字超・空白や制御文字は 400）で、
   このルートは汎用の 300 秒キャッシュではなく**自分でキーを持つ**: 同じキーの同時 2 本は 1 本だけ動き（もう 1 本は
   409 `duplicate_request` / `in_progress`）、成功したキーの再送は時間によらず 409 `duplicate_request` と
   **そのキーが始めたセッション**（`session: { id, current }`）を返す。プロセス内で直近 256 件を覚え、それより古い
   キーと再起動後は忘れる（その場合は新しいリセットとして動く）。ボディは空か `{}` だけ（他は 400 `invalid_body`、
   64 KiB 超は 413）。
   画面側は、結果不明の送信（Stop 後・切断）がある間はボタンも `/new` も使えない（再送か破棄が先。古い会話に
   記録されるかもしれない送信を新しい会話の後に残さない）。逆に**リセットの結果が不明**な間は、メッセージを
   送らない（消える側の会話に入るかもしれないため）。もう一度押すと同じキーで再送し、サーバーの答え（成功・
   「このキーは済み」）か、履歴の `session.request` が**このキーのダイジェスト**と一致したときだけ解決する
   （別タブのリセットで session id が変わっただけでは解決しない）。解決したキーは捨て、次の新しい会話は新しい
   キー。成功（「済み」を含む）の後は、画面は空だと決めつけず履歴を読み直して表示する。読み直しに失敗したら
   古い会話を画面から消し、「新しい履歴を読み込めませんでした。再読み込みしてください」と「再読み込み」ボタンを出し、
   読み直しが成功するまで送信しない（チャット: `historyStale`、Stage: `composerState({historyStale})`）。
3. **監査**: `events.db` に、リセットの**前に**（共有ロックの外で）`session.reset`（`principal: local:operator`・
   接続元・ターン数・新旧のセッション id・要求のダイジェスト）を書く。書けなければリセットせず 500 `audit_failed`
   （事前の健全性チェックが通った後の書込み失敗もこれ）。続けて結果の行を 1 つ: `session.started`（捨てた
   メッセージ数）・`session.reset_refused`（拒否の理由）・`session.reset_failed`。結果の行は 1 回だけ再試行し、
   それでも書けなければ ERROR ログ、応答の `outcome_audit` が `"failed"`（成功なら `"ok"`）。リセット自体は
   `session.reset` 行で追跡できるので、結果の行が書けなくてもやり直さない（同じキーは済み扱い）。会話の中身は書かない。
   **永続化**: `SQLiteEventStore.emit()` は同期で、`BEGIN IMMEDIATE` → INSERT → COMMIT が終わってから戻る
   （WAL、SQLite 既定の `synchronous=FULL`）。書込みエラーは例外として伝わる（握りつぶさない）。データベース
   エラーは以後の書込みも止める（次の `/new` は 503 `audit_unavailable`）。
   **`audit_unavailable` の条件**（`_NewSessionHost.audit_ready()` = `event_store.error is None`）: 立つのはデータベース・
   ハッシュ連鎖のエラー（sticky）だけ。障害が直っても同じプロセスの中では解除されず（フェイルクローズ）、解除はストアを
   開き直したとき（再起動。開くときにファイルを検査する）。一時的な `SQLITE_BUSY` / `LOCKED` はその 1 回が 500
   `audit_failed` になるだけで、次の `/new` は通る。起動時に開けなかった（busy）ストアも書込みのときに開き直す
   ので、前もって拒否しない。テスト: `test_audit_unavailable_after_a_transient_lock_is_not_permanent`、
   `test_a_store_busy_at_open_is_retried_by_the_write`、`test_a_sticky_store_failure_stays_refused_until_the_store_is_reopened`。テスト: 実際の
   event store を `PRAGMA query_only` で読み取り専用にすると 500 `audit_failed`、会話はそのまま（次のターンで
   モデルに渡るメッセージが続きになる）。限界: ハッシュ連鎖の head ファイルは COMMIT の前に書く（既存の設計、
   ADR 0009）。電源断などで WAL の同期が失われた場合は head と行が食い違い、次の起動で検出される。
4. **エージェント自身が叩けないこと（実測）**: エージェントのツールはターンの中で動くので、ターンの lock を
   持ったまま `/new` に届き、必ず 409 `turn_running` になる。実際に `http_request` のルールを Always にし、
   CSRF トークンを持たせ、上流の端末確認も外して（`BYPASS_TOOL_CONSENT=true`、最悪の運用設定）、
   偽モデルに `POST /api/chat/session/new` を呼ばせた結果: ツールの結果は `Status Code: 409` /
   `turn_running`、履歴はそのまま（3 件）、監査行も増えない。既定のままなら `http_request` は Never、
   Always にしても上流の非 GET の端末確認が無人のサーバーでは取り消される（`HTTP request cancelled by
   the user`）。残る経路は実行系ツール（既定で非表示）でターンの後に動くプロセスを残すことで、これは
   他の管理 API と同じ制約（docs/admin-api-permissions.md「agent can reach its own admin API」）。
5. **再起動との比較（実測）**: 2 ターン後に `/new` → 次のターンでモデルに渡るメッセージは 1、
   `/api/chat/history` は 0 件、Neural State・ブレーカー・記憶件数・承認履歴・`/api/turns` は前と同じ。
   再起動後の 1 回目と同じ。

**セッション境界の注意点（実測で分かったこと）**:
- 次のターンはプロンプトキャッシュの履歴部分が外れる（システム部分は残る）。
- `pre_turn` に渡る会話履歴が短くなるので、履歴を読む検出（同調圧の監視など）は新しい会話から数え直し
  （再起動と同じ）。bcScore は Neural State 側の窓なので続く。
- ディスクのチェックポイント（既定で会話の全文、最大 20 世代）とエピソード記憶は消えない。システム
  プロンプトの「最新のエピソード」は新しい会話にも入る（再起動と同じ。新しい会話でも記憶は覚えている）。
- `/api/turns`（`turns.db`）は前の会話のターンも並べたまま。チャット画面の履歴と Stage のログは
  `/api/chat/history` なので新しい会話だけになる。
- 別のタブで開いている画面は、次に履歴を読むまで前の会話を表示している（Stage はログを開いたとき、
  チャット画面は再読み込み時）。

## 12. コンテキストゲージ — ％表示（フェーズ3）

**実測**: 直近ターンの使用量は `POST /api/chat` の `turn` イベントと `/api/chat/history` の各ターンにある
（`input_tokens`・`cache_read_tokens`・`cache_write_tokens`）。`input_tokens` はターン内の**全モデル呼び出しの
合計**（Strands の `accumulated_usage`）で、ツールを 1 回使ったターンは 2 回分（偽モデルで 1000 + 1200 = 2200）。
Strands は呼び出しごとの使用量をイベントループのサイクルに持っている（`agent_invocations[-1].cycles[-1].usage`、
SDK 自身の `latest_context_size` が読む値）ので、**最後の呼び出し 1 回の入力**を `context_tokens` として
ターンに足した（同じ例で 1200。プロバイダごとのキャッシュの数え方は `providers/usage.py` で正規化）。

**入れたもの**: `/api/gateway/status` に読み取り専用の `context_window: { tokens, source, compression_threshold }`
（`resolve_context_window_source`。要約の判定と同じ解決: 設定 `context_window_tokens` → モデル自身の
`context_window_limit` → 能力表 → 既定 200,000＝`source: "default"`）。クライアントは `context_tokens ÷ tokens`
で `ctx NN%`、80% で警告色（`--warn-fg`）。コンテキスト管理が有効なときだけ、閾値の 95% で「自動要約が近い」。
無効なら 80% 以上で「自動要約はオフ」（「近い」とは言わない）。ツールチップに、最後の呼び出しの値か合計か、
窓が既定値の仮定か、要約の設定を書く。窓が無い（古いサーバー）ときはトークン数だけ。

**限界**: `context_tokens` が無い記録（このフェーズより前、またはプロバイダが呼び出しごとの使用量を返さない）は
合計にフォールバックし、ツールチップに「ツールを使ったターンは高めに出る」と出す。窓が `default` のときは
実際の窓と違うことがある（ツールチップに出す）。モデルを切り替えると窓も変わる（ステータスの定期取得で追従）。

## 13. 既定化（`ui.home`）の切替手順とフォールバック

既定は `chat` のまま（フェーズ2 でも変えない）。Stage を主画面にするのは運用者の切り替え:

1. チャットサーバーを `STIRA_STAGE=1` で起動する（`scripts/stira_ctl.sh` なら環境変数で渡す）。
2. ゲートウェイ設定 `gateway-config.json`（`stira_ctl.sh` で起動するなら `<repo>/.local/stira/`）に
   `"ui": {"home": "stage"}` を書き、再起動する（起動時に一度だけ読む）。`/` が Stage になり、サイドメニューの先頭が
   「ステージ」になる。`STIRA_STAGE=1` が無いと `/` はチャットのまま（起動時に警告を出す）。不正な値もチャットに戻る。
3. 戻すときは `"home": "chat"`（または `ui` ごと消す）で再起動。

フォールバック: `/chat` は常にある。JavaScript 無効 → `<noscript>` でチャットへのリンク。WebGL が使えない →
部屋とキャラの静止画（キャラは休止姿勢を CPU で合成）＋「WebGL が使えないため静止画で表示しています。チャットで開く」、
入力・バックログ・ボード・承認はそのまま使える（ボードは静止画の手前）。`prefers-reduced-motion` → ボードの上げ下げ・
キャラの移動・タイプライターは即時。
