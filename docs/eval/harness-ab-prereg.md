- Issue: #698。関連: #686(指標を比較に使う)、#368(最初の被験)、#280(記録の形式)、#315 / #457(読み取りの床)、ADR 0011(grant)、ADR 0019(`run_checks`)。
- 版 1(2026-11-10)。**最初の実行より前にコミットする。** 変更は末尾の「変更と逸脱」に理由つきで追記し、上の本文を黙って書き換えない。
- 状態: **手順の登録のみ。A/B はまだ 1 回も走っていない。** §9 の未決事項が埋まるまで実行しない。

> この手順で言えるのは「この課題・このモデル・この設定で、基準を満たした / 満たさなかった」まで。
> 件数が少ない(dev 6 + held-out 3)ので、基準を満たさない結果は「効果なし」ではなく「基準未達」と書く。
> 満たした結果も「この課題集合とこの設定で達成」と書き、一般化しない。
> 証拠にしないもの: エージェント自身の完了報告の文章、「良くなった気がする」という印象。

## 1. 目的と対象

ハーネスの変更(システムプロンプト、ツールの説明、ルーティング)を採用するかどうかを、固定した課題で A と B を比べて決める。

- **A** = 基準のコミット。**B** = A に**変更を 1 つだけ**足したもの。2 つ以上を同時に変えない。
- 課題、モデル、推論設定、grant の設定、反復回数は A と B で同じ。
- 安全側の仕組み(認可、承認、Breaker、床、egress、マスク)を変える変更は、この手順の対象外(ADR で決める)。

## 2. 課題

- `run_checks`(ADR 0019、`pytest`)で合否が決まる小さなコード課題。**dev 6 件 + held-out 3 件**。
- 1 課題 = 目標文(grant の `goal`)、初期ファイル、参照テスト。参照テストは運用者の手元にも原本を置く(§4 の判定で使う)。
- 課題 ID は中身を示さない名前にする(dev: `d1`–`d6`、held-out: `h1`–`h3`)。
- **dev** はハーネスを変更する人・コーディングエージェントが見てよい。調整は dev だけで行う。
- **held-out** は、ハーネスを変更するコーディングエージェントが**書かず、読まない**。人間(または調整に関与しない別の作業者)が作る。
- 実行前に、全課題の SHA-256 の一覧(マニフェスト)を固定する。held-out のマニフェストは ID とハッシュだけをリポジトリに置く(本文は置かない)。

## 3. held-out の隠し方

隠す相手は 2 者で、守り方が違う。

### 3a. ハーネスを変更するコーディングエージェント(主な相手)

コーディングエージェントは shell を持つことが多く、同じ OS ユーザーで読めるものはすべて読める。Stira の床は関係しない。

- held-out は**リポジトリの外、すべてのワークツリーの外**に置く。
- コーディングエージェントを動かす OS ユーザーから読めない場所に置く(別の OS ユーザーの `0700` のディレクトリ、または held-out の実行のときだけマウントする暗号化ボリューム)。**未検証**: どちらを使うかは §9。
- held-out の実行で生じるもの(データディレクトリ、ワークスペース、会話の記録、ログ)も課題の本文を含むので、同じ扱いにする。リポジトリに入れるのは §6 の許可リストの欄だけ。

### 3b. 被験の Stira エージェント(課題を解く側)

被験エージェントは、自分が解いている課題の目標文・初期ファイル・ワークスペース内のテストは見る。見せないのは、**他の課題**と**運用者の手元の参照テスト原本**。

コードとテストで確認したこと(2026-11-10、このワークツリー):

| 経路 | 結果 | 根拠 |
|---|---|---|
| `file_read`、`view_image`、`image_reader`、`editor` の `view`、`lsp_diagnostics`、`lsp_hover` でワークスペース外を直接読む | 拒否(`E_READ_OUTSIDE_ROOTS`)。`read_roots` が既定(ワークスペースのみ)のとき | `tests/test_read_roots.py::test_outside_the_workspace_is_refused_by_every_read_tool`(実行して 6 件とも通過) |
| `image_reader` の 2 度目の open、`lsp_*` が解析器に名前を渡す(#315 の窓) | 閉じている(確認済みのバイト列を渡す) | `docs/research/read-floor-2026-10-16.md`、`tests/test_read_floor_windows.py`(実行して通過。入れ替えの実測そのものは 2026-10-16 のもので、今回はやり直していない) |
| `lsp_*` の解析器が**名前で読む別のファイル**(隣の設定、import したモジュール、スタブ) | **床なし。隠せない。** ワークスペース外の Python ファイルは、相対 import などで名前・シグネチャ・リテラル値が診断に出る | ADR 0010 の「Residual risk」(2026-10-16 計測。今回は再計測していない) |
| `run_checks`(macOS のプロファイル)でエージェントが書いたテストから読む | ホームディレクトリの下は読めない(実行用コピーとインタープリタの場所を除く)。**ホームの外(`/tmp`、`/Users/Shared`、外付けボリュームなど)は読める** | `src/stiracore/tools/run_checks.py` の `sandbox_profile`(コードを読んだだけ。今回は実測していない) |
| `run_checks`(Linux、limits のみ) | 隠せない(ADR 0019 の脅威表)。grant も `run_checks` を含む範囲を拒否する | `docs/grants.md` |
| exec 系ツール(`shell` など) | 有効にすると OS ユーザーの権限で何でも読める | AGENTS.md |

ここから決める条件:

1. 被験の実行は **grant の反復**で行い、`scope.tools` は `file_read`、`editor`、`run_checks` だけにする(`lsp_*` は grant の範囲に入れられないので、上の「床なし」の経路は開かない)。
2. `read_roots` は既定のまま。`STIRA_ENABLE_EXEC_TOOLS` は設定しない。
3. 実行中のホストに、そのとき解いている 1 課題以外の課題を**サーバーの OS ユーザーが読める形で置かない**。やむを得ず置く場合も、ホームディレクトリの下で、ワークスペース・データディレクトリ・インタープリタ(venv)の外に限る。`/tmp` などホームの外には置かない。
4. 実行ごとに新しいデータディレクトリを使う(記憶を通じて課題間・条件間で情報が移らないようにする)。

**未検証**: 3 の「ホームの下なら `run_checks` から読めない」は今回実測していない。プロファイルが拒否するのはファイルの**中身**の読み取りで、名前や存在が分かるかどうかも未確認。このため第一の手段は「置かない」(3 の前半)とする。

## 4. 指標

1 回の実行 = 1 課題 × 1 条件 × 1 反復番号(新しいデータディレクトリ、新しい grant 1 件)。

| 指標 | 定義 | 出所 |
|---|---|---|
| 受け入れ | grant が終わった後、運用者が成果物のコピーに**参照テストの原本を戻して**同じチェックを走らせ、終了コード 0 かつ 1 件以上のテストが通過 | 運用者の実行(A と B で同じコマンド。実行表に固定) |
| 受け入れ率 | 受け入れた実行数 / 実行数(dev と held-out を別々に) | 上から計算 |
| 1 件あたりトークン | その実行の grant で課金されたトークン(予算の合計 − 残り) | `GET /api/grants/<id>` の構造化された状態 |
| 反復数 | 「1 反復を実行」を押した回数 | 運用者の記録 |
| 介入回数 | 手順に定めた操作(発行、ホスト確認、反復の実行、最後の検証)**以外**に人が行った操作の数(一時停止、再開、`RESUME`、発行のやり直し) | 運用者の記録 |
| 承認カード数 | その実行で出た承認カードの数 | 監査の `audit.approval.requested` の行数 |

- エージェント自身の `run_checks` の結果と完了の主張は、合否に使わない(テストを書き換えれば緑にできるため)。参考値として `claim_evidence` のコードだけを記録する。
- 放棄された呼び出し(`abandoned_call`)は予約の全額が課金されるので、その実行は `abandoned_calls` を記録し、トークンの比較では別に示す。
- **未検証**: 上の「出所」の欄名は docs から拾ったもので、#686 の実装と突き合わせていない(§9)。

## 5. 実行の手順

1. **差分の事前確認(モデルを呼ばない)。** A と B で、grant の反復が最初に送るリクエストを比べる。**バイト単位で同じなら実行しない**(差が出ない変更にトークンを使わない)。
2. 固定するもの(実行表に書く): A と B のコミット、モデル ID とリージョン(Bedrock)、推論設定、`prompt_cache`、grant の `total_tokens` / `per_tick_tokens` / `ttl_sec` / `max_iterations`、ホスト(macOS、`os_sandbox` が検証済み)。
3. 各課題 × 各条件を **k 回**。順序は課題ごとに A, B, B, A(時間による偏りを打ち消す)。grant は 1 サーバ 1 件なので直列。
4. 1 回の実行: 新しいデータディレクトリ → 課題をワークスペースに置く → grant を発行(ホスト確認)→ 完了の主張が出るか `max_iterations` に達するまで反復を実行 → §4 の判定 → §6 の記録を 1 行書く。
5. **dev を先に全部走らせる。** dev で §7 の基準を満たさなければ、held-out は走らせない(held-out を使い減らさない)。
6. **held-out は候補 1 つにつき 1 回だけ採点する。** 結果を見た後にその変更を調整したら、新しい候補として扱い、held-out の使用回数に数える。同じ held-out を 3 候補に使ったら作り直す。

提案する値(最初の実行の前に §9 で確定): k = 2、`max_iterations` = 4、`total_tokens` = 120,000。このとき実行数は 9 × 2 × 2 = 36、トークンの上限は 36 × 120,000 = 4,320,000(grant の予算による上限。実際の使用量は 1 反復 2.7k〜28k という 1 回のスモークの推定しかなく、**見積もりであって計測ではない**)。

## 6. 記録の形式

1 実行 1 行の JSON Lines。**許可リストの欄だけ**を書く。目標文、課題の本文、モデルの出力、テストの出力、パス、秘密は書かない。

| 欄 | 内容 |
|---|---|
| `prereg_version` | この文書の版 |
| `subject` | 被験の Issue 番号(例 `368`) |
| `arm` | `A` / `B` |
| `commit` | その条件のコミットのハッシュ |
| `task_id` / `split` | `d1`…`h3` / `dev`・`heldout` |
| `manifest_sha256` | 課題マニフェストのハッシュ |
| `rep` | 反復番号(1…k) |
| `model_id` / `region` | 固定した値 |
| `accepted` | `true` / `false` |
| `check` | 参照チェックの終了コードと件数(`exit_code`、`passed`、`failed`) |
| `tokens` | 課金されたトークン |
| `iterations` / `interventions` / `approval_cards` / `abandoned_calls` | 回数 |
| `end_code` | grant と goal の終了のコード(例 `ended(complete)`、`blocked(max_iterations)`) |
| `claim_codes` | `claim_evidence` のコード(文章は含めない) |
| `rerun_of` / `rerun_code` | やり直しの場合、元の行と理由のコード |
| `ran_at` / `host_class` | 実行日(UTC)、`macos-os_sandbox` |

置き場所: `docs/eval/harness-ab/<日付>-<被験>.jsonl` と、同じ名前の短い報告(`.md`、基準ごとに「達成 / 未達」)。

**未検証**: #280(receipt)の形式を定めた文書はこのワークツリーに見つからなかった。上の表は「コミット・コマンド・件数・日付を機械的に残す」という方針に合わせた案で、#280 の欄名との一致は確認していない(§9)。

## 7. 採用の基準

変更ごとに、**主指標を 1 つ**、実行の前に実行表で宣言する(受け入れ率を上げる変更なら受け入れ率、トークンを減らす変更なら 1 件あたりトークン)。

B を採用するのは、**dev と held-out のそれぞれで**次をすべて満たすときだけ。

| 種類 | 基準 |
|---|---|
| 主指標が受け入れ率の場合 | B の受け入れ数 > A の受け入れ数 |
| 主指標がトークンの場合 | B の 1 件あたりトークンの中央値 ≤ A の 0.95 倍、**かつ** B の受け入れ数 ≥ A の受け入れ数 |
| 雑音の床 | 主指標の差が、A の反復どうしの差(同じ課題の A の 1 回目と 2 回目の差を集計したもの)より大きい。小さければ「雑音以内」と報告し、採用しない |
| 悪化させない | 介入回数の合計と承認カード数の合計が、B ≤ A |

- dev だけ満たして held-out で満たさない場合は不採用(dev への合わせ込みとみなす)。
- 有意性の検定は行わない(件数が足りない)。数値は全件を報告する。

## 8. 除外とやり直し

- 実行を除外しない。全行を報告する。
- ハーネスの外の失敗(grant の発行が拒否された、プロバイダのスロットリング、ホストの障害)に限り、その実行を 1 回だけやり直す。元の行も残し、やり直しの行に `rerun_of` と理由のコードを書く。
- モデルの失敗(テストが通らない、反復の上限、予算切れ)はやり直さない。不合格として数える。

## 既知の限界

- 件数が少ない。k = 2 のとき、1 回の実行の合否で受け入れ率が dev で約 8 ポイント、held-out で約 17 ポイント動く。
- モデル 1 つ、Bedrock のみ、macOS のみ(`run_checks` を grant で使える条件)。他の環境には当てはめない。
- grant は発行ごとにホスト確認が要るので、36 回の実行には 36 回の人の操作が要る(これは介入に数えない)。
- 受け入れの判定は運用者の実行で、被験エージェントの `run_checks` そのものではない(§4 の理由)。
