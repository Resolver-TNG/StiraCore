# 権限サービス（ADR 0011 §5・§12、W1 + W2）

**状態:** ADR 0011 §13 項目 2（共通の安全基盤）の一部として実装済み: W1（サービス、永続の
エポック）と W2（ラッチストア、ライフサイクルイベントとアウトボックス、モデルを使わない
ウォッチドッグ、キルスイッチのルート）。これ自体は何の作業も始めない。これによって新しく
動くものは無い。目標グラントとゴール反復の実行部（ステージ C、ADR 0011、**アルファ版**、既定
オフ）はこの上に作られている — [grants_ja](grants_ja.md) と概要 [autonomy_ja](autonomy_ja.md)
を参照。`halted:*` ラッチを立てるものはまだ無い（グラントは再起動を越えない）。English:
[authority-service.md](authority-service.md)。

## 何か

サーバープロセスごとに 1 つの `AuthorityService`（`src/stiracore/authority/`）。すべての
サブシステムが共有する、ただ 1 つの権限の境界。

| 部分 | 役割 |
|---|---|
| インカーネーション | プロセスごとに 128 ビットの乱数（`stiracore.authority.incarnation`）。ハートビートの `INCARNATION` と YOLO のデスクも同じ値を使う。書き出さず、読み戻さない。 |
| 許可証 / `consume` | 効果 1 回につき許可証 1 枚。インカーネーション、種別（`goal` / `yolo`）、グラント ID、世代、エポック、監査レシートに結びつき、ちょうど 1 回だけ消費する。任意の結びつき: ポリシーの版、予算の予約 ID、TTL の組（壁時計と単調時計の期限）— W5 の目標の反復の実行部が TTL の組と（モデル呼び出しでは）予約 ID を結ぶ（[grants](grants_ja.md)）。 |
| 権限エポック | 単調増加。狭める操作のたびに進む: プロセスの起動、ツール規則の保存、ブレーカーの NORMAL 以外への変化と NORMAL 以外どうしの変化、キルスイッチ、YOLO 自身の動き（一時停止・終了・停止・`/new` など）。進む前に出た許可証は拒否される（`epoch_moved`）。 |
| キルフラグ | ロックを取らずに最初に立て、`consume` が最初に読む。その後でエポックが進む。他のスレッドがどのロックを持っていても効く。その後で `kill` ラッチを永続化する（W2）: 人間が解除するまで、再起動しても止まったまま。`POST /api/authority/kill` で立てる。ステージ C がオンなら、設定 → 目標グラントの「キルスイッチ（すべて停止）」ボタンがこれを送る。 |
| 実行中の集合 | 効果は `consume` のときに取消コールバックを登録できる。後から狭める操作がロックの中で集合を取り、ロックを放してからコールバックを呼ぶ。停止の後に終わった効果は `completed_after_stop` として記録する。上限 64。5 秒を超えて走るコールバックは見捨てる（W2、下記）。 |
| 不健全（unhealthy） | 閉じる側に倒す: その間、許可証の発行と `consume` はすべて拒否（`authority_unhealthy`）。理由コードは `AuthorityService.status()` に出る。 |

YOLO のデスクはこのサービスを注入で受け取る（`yolo.runtime.install_host(authority=…)`）。
自動承認はこの許可証を使う。YOLO が off でもサービスは存在し、ツール規則の保存やブレーカー
の変化でエポックは進む。

## `authority-epoch` ファイル

データディレクトリの中、モード `0600`。flush（macOS では `F_FULLFSYNC`）→ 原子的な
rename → ディレクトリの flush で書く。最新 16 件の記録を持ち、各記録は `seq`（書くたびに
1 つ）、`epoch`、`prev`（前の記録のハッシュ）、`hash`。起動時のエポックは保存値 + 1（使う
前に書く）。**ファイルが無ければ初回起動**（エポック 1）。エポックの値は起動をまたいで一意では
ない: 狭めた後の書込は遅らせてまとめるので、プロセスが落ちたとき（`SIGKILL` など）にまだ
書いていなかった値は、次のプロセスがもう一度出しうる。起動をまたぐ同一性は常に
`(インカーネーション, エポック)` で、エポックだけでは決めない。

ファイルはシンボリックリンクをたどらず、ブロックせずに（FIFO でも）開き、開いた記述子を
もう一度確かめる（通常ファイル、この利用者、モード `0600`、リンク 1 本、パスと同じデバイス・
inode・サイズ・変更時刻）。置き換える前には毎回いまのファイルを読み直し、このサービスが最後に
書いたものと完全に同じ（同じバイト、そして自分の書込みと rename の後に記録したデバイス・inode・
サイズ・`st_ctime_ns`）でなければ何も書かない。変更時刻を同一性に含めるのは、Linux（ext4、
tmpfs）が解放された inode 番号をすぐ次の新しいファイルに渡すため: 同じバイトでの削除と作り直しは
inode 番号を保っても変更時刻は保たない（#661）。ラッチストア、ライフサイクルログ、outbox、
ウォッチドッグの記録、グラントストアも同じ同一性を使う。

| 理由コード | 意味 |
|---|---|
| `epoch_store_unsafe` | この利用者の、リンク 1 本の通常ファイルでモード `0600` 以下、ではない（シンボリックリンク、`0644` など） |
| `epoch_store_unreadable` | 開けない・読めない |
| `epoch_store_malformed` | 形式が違う |
| `epoch_store_hash_mismatch` | 記録のハッシュか `prev` のつながりが合わない |
| `epoch_store_sequence_gap` | `seq` が欠けている・重なっている |
| `epoch_store_not_monotonic` | エポックが増えていない |
| `epoch_store_replaced` | 動いているサービスの裏でファイルが置き換え・変更・削除された |
| `epoch_store_write_failed` | 書込に失敗した（ディスクがいっぱい、権限など） |
| `epoch_settle_unavailable` | 遅らせた書込を片付けるワーカーを起動できなかった（作業は待ち行列に残る） |
| `epoch_settle_failed` | 遅らせた片付けが失敗した |

壊れたファイルは上書きしない。後で書込が成功しても状態は戻らない。人間が見るまでプロセスは
不健全のまま。**直し方**（*エポックのファイル*そのものが壊れたときだけ。壊れた・古いラッチ
ストアは `reset-latches` だけで直し、このファイルを消して直すことは決してしない）: サーバー
を止め、記録のためにファイルを写してから消し、`stira authority reset-latches` を実行し
（すべてのラッチを立てる: コミットメントが無ければ古いラッチストアは信用しない）、起動し
直し（エポックは新しいインカーネーションで 1 から。以前のものは何も受け付けない）、解除する。不健全の間、
YOLO は何も自動承認しない（『確認』はすべてカードになる）。

**限界。** ハッシュの鎖が見つけるのは破損と順序の乱れで、同じ利用者による改ざんではない:
鍵の無い SHA-256 なので、サーバーと同じ利用者のプロセスなら正しい鎖を書き直せる。そうした
プロセスは 2 つの確認の間にファイルやディレクトリをすり替えることもできる。確認はその隙を
狭めるだけで、閉じはしない（データディレクトリはエージェントの床の中なので、エージェント自身
のファイルツールでは書けない）。データディレクトリ全体を、より古い正しいファイルに戻された
ことはここでは検出できない。起動をまたぐ同一性は常に `(インカーネーション, エポック)`
（ADR 0011 §5、Open (6)）。

## ロックの順序

1 つの葉ロックがメモリ上の比較と設定だけを守る。持っている間は I/O もコールバックも時計の
読み取りも他のロックの取得もしない。呼び出し元は自分のロックを持ったまま呼んでよい
（スケジューラのロック → 権限ロック、YOLO の要求ロック → 権限ロック、エンジンの
`state_lock` → 権限ロック）。永続化（専用の I/O ロック）と取消は葉ロックを放してから行う。
ノンスと効果 ID は葉ロックを取る前に作る。狭める操作はどれも、エポックを進めるのと同じ一歩で
1 つの束（そのエポックと、取った実行中の効果）を待ち行列に入れる。束を片付けるのは常に 1 人の
持ち主で、順番どおり: 片付けワーカー（他のロックの下での狭め — YOLO の動き、ブレーカーの
フック。これらは例外を投げない）、ツール規則の保存とキルスイッチ（他に持ち主がいなければ
呼び出したスレッドで）、ワーカーを起動できないときの期限なしの `flush_result()`。束ごとに
取消してから書く。取消がまだ動いているエポックはファイルに出ない（*前線*）。ワーカーを起動
できなければ `epoch_settle_unavailable` でラッチし、作業は待ち行列に残る。メモリ上の狭めは
I/O より前に効き、書込に失敗しても元に戻らない。停止時の `authority` の段は持ち時間の中で
すべての持ち主を待つ: 何も残らず**かつ**エポックがディスクにあるときだけ `stopped`、それ以外は
`pending`（作業が残った）、`unhealthy`（片付いたが永続化されていない）、
`pending (no settle worker)`。`StiraCore: stopped (...)` の行に `authority` が出るのは
`stopped` でないときだけで、きれいに止まれば行は従来どおり。

YOLO の発行は、`issuing` の公開と共有エポックの読み取りを葉ロックの中の一歩で行い、最後の
確定も同じロックの中で、エポックが変わっていないときだけ行う（`commit_at_epoch`。時計・健全性・
ブレーカー・緩めの判定はその前に集める）。その間に動けば（ブレーカーの
変化、ツール規則の保存、キルスイッチ）`issue_aborted_epoch` で終わる（ADR 0012 §6a / §6b）。
ツール規則の保存は先に YOLO を止め、それからエポックを書く。サービスが kill 済みまたは不健全
のために拒否した許可証は、`audit.yolo.void` に `killed` / `authority_unhealthy` として残る。

**ハードリンクのバックアップ。** `authority-epoch` へのハードリンク（同じボリューム上のハード
リンク式バックアップなど）はファイルを安全でないものにする: 次の書込で `epoch_store_unsafe`
になり、リンクを消して再起動するまで不健全のまま。データディレクトリはハードリンク式の
バックアップから外すこと。

**取消コールバックの時間の区切り（W2）。** 片付けは順番に進むので、1 つのコールバックが
止まると後の取消もエポックの書込もその後ろで待つ。`narrow()` とキルスイッチは**呼び出し元
のスレッドで取消コールバックを決して走らせない**: コールバックのあるバッチは片付けの
ワーカーに渡し、呼び出し元は最大 `SETTLE_WAIT_SEC`（1 秒）だけ待って、終わらなければ
`settlement: cancelling` を返す（`narrow_result()` / `kill_switch()`。取消が終わりエポック
がディスクにあれば `settled`）。`CANCEL_DEADLINE_SEC`（5 秒）を超えて走っているコール
バックは**見捨てる**: ウォッチドッグの一巡（または停止時などの `flush_result`）が止まった
持ち主からキューを取り上げ、そのバッチの残りを先頭に戻し、効果を `cancel_overdue` として
記録し（効果は終わるまで実行中の集合に残る）、サービスを**不健全**にし（`cancel_overdue`:
取消を確かめられない）、新しいワーカーが残りを片付ける。見捨てたコールバックは戻るまで
数え続ける（status の `cancel_abandoned`）: その間 `flush_result` は `pending`（`clean` に
は決してならない。期限なしなら即座に）、片付けはすべて `cancelling`。戻った後、止まって
いたスレッドはもう何も触らない（バッチの残りを 2 回走らせることはない）。

## ラッチ（`authority-latches`、W2）

プロセスを越えて残る停止のラッチ。**解除できるのは人間だけ**（下記）。名前は固定でコード
のみ: `kill`、`unhealthy`、`halted:<理由>`（`<理由>` は `breaker`、`emotional`、`identity`、
`budget`、`clock_anomaly`、`unhealthy`、`restart_conflict` のどれか。W2 では `halted:*` を
立てるものは無い。グラントがまだ無い）。立っているラッチはそれぞれ、立てたときの
**停止 ID** `(インカーネーション, エポック)` を持つ。

* 起動時: `kill` が立っていればキルフラグが立った状態で始まり、`unhealthy` が立っていれば
  不健全（`latched_unhealthy`）で始まる。
* サービスが不健全になると（理由を問わず）、ウォッチドッグが `unhealthy` を永続化する。
* **キルの規則は 1 つ**: フラグ、エポック、永続化の試み——第二の印（`authority-kill-armed`
  を `authority-kill-fired` に名前を変える。空きブロックの要らない rename）、`kill` ラッチ、
  そのエポックファイルへの約束（コミットメント）——その後でキル自身の取消コールバックを、
  順に、**専用の実行器**で走らせる: 片付けのキュー、その持ち主、そのエポックの書込を
  決して通らないので、ハングしたディスクも I/O で止まった持ち主もそれを止めない。対象は
  キル自身の作用**と**、今の持ち主の後ろにまだ積まれている狭めの作用（W4.5、#618 K1）。
  持ち主がすでに走らせているバッチはその持ち主に残る（そこで期限を過ぎたものは下のとおり
  見捨てる）。各
  コールバックは最大 `CANCEL_DEADLINE_SEC` 待ち、まだ走っていればそのまま残し
  （`cancel_overdue`。戻るまで数える）、次を始める。エポックは他の狭めと同じに片付ける。起動時に印が発火していれば停止の状態で始まり、`kill` の無い
  ラッチストアは拒否する。`stira authority unlatch kill` が印を消す（次の起動で再び
  用意する）。
* **残る弱点（ディスクが満杯）:** `unhealthy` ラッチにはこの第二の印が無い。その書込に
  失敗するとプロセスはメモリ上で不健全になりそれを示す（status、停止の行）が、満杯の
  ままの再起動は、ライフサイクルのログにイベントが残っていなければ健全で始まりうる。
  キルには印が残る——ただし印が用意されていること: 起動時に作れない、または安全でない
  エントリ（シンボリックリンク、ハードリンク、FIFO、ディレクトリ、別の所有者、`0600` より
  広い）がある場合は不健全（`kill_marker_unavailable` / `kill_marker_unsafe`）。rename
  自体も最善の努力で、すべての操作に失敗するファイルシステムでは何も残らない。
* **永続化の試みには期限があり、同時に 1 つだけ:** 試みは一度に 1 つ（ハング中に押された
  キルはそれを待つ。キルごとのスレッドは作らない）、最大 `KILL_PERSIST_DEADLINE_SEC`
  （5 秒）待つ。過ぎれば取消はそのまま走り、キルは立ったまま、サービスは不健全
  （`kill_persist_timeout`。アウトボックスとキルの答え `latch: timeout` にも出る）。
  スレッドを始められなければ永続化をその場で走らせることは決してしない
  （`kill_persist_unavailable`）。その試みは**動いているウォッチドッグに渡し**、次の一巡の
  最初に印とラッチを書く（キルのイベントで起こされる）。答えは `latch: pending`（待っている
  間の後のキルも同じ）。ラッチがディスクに載るまで `status()` は `kill_durable: false` を示す
  （W4.5、#618 K2）。キルのライフサイクル記録（とグラントの後処理）は、永続化の試みと取消の
  開始の後でだけ積む（#620 W5-3）。同じプロセスで後から書けたものはキルを足すだけ。別の
  プロセスは割り込めない（データディレクトリの `server.lock`）。
* **コミットメント（削除や巻き戻しで黙って外れない）。** エポックの記録はそれぞれ、ラッチ
  ストアの世代、最新の記録のハッシュ、乱数の**ストア ID**（`latch_gen`、`latch_head`、
  `latch_store`）も持つ（起動時、エポックを書くたび、キルと `unhealthy` のラッチの直後、
  `unlatch` が書く）。世代は鎖に沿って減らない——`reset-latches` は世代を続け、新しい
  ストア（新しい ID）を約束された先頭につなぐ。起動時にストアは約束から**つながって**
  いなければならない: 約束された記録（同じ世代・ハッシュ・ストア ID）を持つか、それを
  直接続ける。無い・古い・同じ世代で中身が違う・別の個体（リセット前のバックアップ）の
  ストアは拒否する（`latch_store_rolled_back`: すべてのラッチが立っている）。
  ライフサイクルのログが「立てて、解除（`human_unlatch`）していない」と示すラッチを
  持たないストアも同じ。コミットメントより新しいもの（2 つの書込の間のクラッシュ、
  オフラインの解除）は受け入れる。W1 時代のディレクトリ（まだコミットメントが無い）は
  1 回だけそのまま受け入れ、その起動で約束する。
* ファイルはエポックのファイルと同じ規則（`0600`、flush、原子的な rename、ディレクトリの
  flush。最新 64 件の記録で、各記録は状態全体と変更を持ち、`seq` と前のハッシュで鎖に
  なる。置き換える前に読み直す）。**読めない・安全でない・形式が違う・合わないファイルは
  すべてのラッチが立っているものとして扱う**（止まり、かつ不健全）。これはプロセスの間
  続き、ファイルは上書きしない。ファイルが無いのを初回の起動とみなすのは、何も約束されて
  いないとき（上記）だけ。データディレクトリ**全体**（エポック、ラッチ、ログをまとめて）
  の古い有効な状態への巻き戻しは、ここでは今も検出できない（ADR 0011 Open (6)）。

| 理由コード | 意味 |
|---|---|
| `latch_store_unsafe` / `_unreadable` / `_malformed` / `_hash_mismatch` / `_sequence_gap` | エポックのファイルと同じ |
| `latch_store_replaced` | サービスの裏でファイルが変わった |
| `latch_store_write_failed` | 書込に失敗した（例: キルのラッチ。プロセスは止まったまま） |
| `latch_store_rolled_back` | ストアがコミットメントより無い・古い・違う、またはログが立っていると示すラッチが無い |
| `latched_unhealthy` | 起動時に `unhealthy` ラッチが立っていた |
| `cancel_overdue` | 取消コールバックを期限を過ぎて見捨てた |

## ライフサイクルイベントとアウトボックス（W2）

`lifecycle_event` のスキーマは 1 つ（ADR 0011 §12）。**コードと ID だけ**: `event_id`、
`subject_kind`（`authority`、`latch`、`breaker`、`yolo_window`、`heartbeat`、`gateway`）、
`subject_id`（種類ごとに検査: 決まった語、ラッチ名、32 桁の 16 進のウィンドウ ID）、
`from`・`to`（決まった状態）、`reason_code`（決まった一覧）、`incarnation`、`epoch`、
`ts_wall`、そして `gateway_down` のときだけ空白の始まり `gap_from_wall`。それ以外のキー、
自由文の値、`str` のサブクラスは拒否する。ゴールの文、ツールの引数、メッセージは入れられ
ない。

今の発生元: キルスイッチ（`latch: cleared → set`、`kill_switch`）、ブレーカーの NORMAL
以外への変化と NORMAL 以外どうしの変化（`breaker`）、YOLO ウィンドウの一時停止と終了
（書かれた後の監査行から観察する。YOLO は変えない）、`unhealthy` ラッチ、ウォッチドッグ
（`heartbeat_stale` / `heartbeat_resolved`、`gateway_down`）、`stira authority unlatch`
（`human_unlatch`）。発生元はキューに積むだけ（I/O しない。ブレーカーの変化はエンジンの
ロックの中で起きる）。書くのはウォッチドッグのスレッド、キルのルート、最後の停止段。

* **ログ** `authority-lifecycle.jsonl`: イベントごとにハッシュの鎖でつないだ JSON 1 行。
  1 行ずつ追記して flush し、同じ安全な開き方の規則を使う。鎖が切れる・最後の行が途中で
  切れる・安全でない・置き換えられたファイルは使えなくなる（続く。ここでは直さない）。
  ウォッチドッグの一巡ごとに、両方の区切りを、書いた・閉じたときのダイジェストと比べる。
  **書くときに上限を守る（オフラインのホストコマンドも含め、すべての書き手）:** 追記で
  1 MiB を超えるなら、先に `authority-lifecycle.1.jsonl`
  に移し（古い方を置き換え）、鎖は新しいファイルで続く。読む側は 1 区切り 2 MiB まで
  受け入れるので、書いたものは必ず開き直せる。
* **アウトボックス** `authority-outbox.json`: 重複除去キー *対象 + インカーネーション +
  エポック + to* ごとに通知 1 件。既読にする（`POST /api/authority/outbox/ack`、その通知の
  **最新の**イベント ID で——透かし（watermark）: 再送や古い既読は何も変えず、より新しい
  出来事のある通知の古い ID は `outbox_stale`。古い既読で繰り返しが隠れることはない）まで
  未読のままで、再起動しても残る。起動時とウォッチ
  ドッグの一巡ごとに作り直す: ログにあるイベントにはすべて通知があり、記録の無い停止を
  持つラッチには `stopped (reason_not_recorded)` を作る。ファイルは通知済みの ID と既読の
  ID（墓標。ログに残っているものだけ）も持つので、既読や間引いた通知が未読に戻ることは
  なく、古い既読の ID にも（そのイベントがログにある間は）`already` と答える。通知は最大
  256 件: 既読から先に消し、それでも多ければ古い未読の*お知らせ*を理由コードごとの件数
  つきの未読 1 件にまとめる。**停止の通知**（ラッチ、権限、停止・不健全への遷移、キル・
  リセット・解除、YOLO の異常終了）は他とまとめない: **停止コード**ごとに 1 件——対象の
  種類、決まった対象の ID（ラッチ名、`service`）、理由コード。ウィンドウ ID もインカー
  ネーションも含めないので、数は決まったコードの数で上限がある。繰り返しは数え、最初と
  最新のイベント ID を残し、最新の出来事を示し、再び未読にする。未読が
  黙って消えることはなく、読む側が拒むような書込もしない。
* **書込の失敗は握りつぶさない**: サービスは `unhealthy` になり（`lifecycle_write_failed`、
  `outbox_write_failed`、`lifecycle_queue_full`、`lifecycle_event_invalid` など）、警告が
  ログに出て、停止の行に `authority_watchdog: unhealthy` が出る。

## ウォッチドッグ（W2）

スレッド `authority-watchdog` が 1 つ。ハートビート、YOLO、ページの表示から独立していて
（YOLO が off でも動く）、15 秒ごと、そしてイベントが積まれたときはすぐに一巡する。モデル、
エージェント、スケジューラ、ハートビート、YOLO のコードは import しない（テストが import の
グラフをたどる）。作業を始めることもない。正確には、**ウォッチドッグ自身はモデルのコードを
import も呼び出しもしない**: ウォッチドッグと権限パッケージは、モデル・エージェント・
プロバイダ・スケジューラ・ハートビート・YOLO のコードを import しない。すべてのモジュール
と親パッケージをたどるグラフ検査と、ルートの入口だけを差し替えたまっさらなインタプリタの
両方で確かめる（`stiracore.authority…` として import すると、先にルートの
`stiracore/__init__.py` が走り、エージェントを再公開している。サーバーではどのみち読み
込まれている。この入口だけが、文書にした唯一の除外）。`start()` の 2 回目は拒否し、
`stop()` の後の `start()` はまた動く。一巡: **ファイルそのものを読み直す**——エポック、
ラッチストア、ライフサイクルのログ、アウトボックスを、同じ安全な開き方で、プロセスが最後
に読んだ・書いたものと比べる。変わった・壊れたファイルは即座に権限を不健全にし（変わった
ラッチストアはすべてのラッチも立てる）、以後ロックを取らない許可証の検査が拒否する（その
前にまず、自分のスレッドを始められずに渡されたキルの永続化を書く）。期限
を過ぎた取消コールバックを見捨てる。
ハートビートの読み取り専用の `status()`（有効で動いていない、劣化している、
`max(3 × 間隔, 120 秒)` の間 tick が無い → `heartbeat_stale`、健全に戻る →
`heartbeat_resolved`）。`unhealthy` を永続化する。積まれたイベントを書く。アウトボックスを
直す。自分の最後の一巡を `authority-watchdog.json` に書く。起動時に、前の一巡が 30 秒
（間隔の 2 倍）より古ければ、その空白を `gateway_down` として記録する。一巡の失敗は
`unhealthy`（`watchdog_failed`）、読めない・書けない記録は `watchdog_record_failed`、
始められないスレッドは `watchdog_unavailable`。**限界:** プロセスが落ちている間は何も記録・
通知されない。空白は次の起動で記録される。

## ルート

`GET /api/authority/status`（読み取りのみ: `healthy`、`unhealthy_reason`、`killed`、`epoch`、
`persisted_epoch`、`settle_pending`、`cancel_overdue`、`in_flight`、`latches`（コード）、
`latch_store_healthy`、`outbox_unread`、`lifecycle_healthy`、`watchdog`。プロセス内の `kill_durable`
はこの応答に**含まれない** — 耐久的になったキルは、`latches` に `"kill"` があり
`latch_store_healthy: true` であることで分かる。既知の制限を参照）、
`POST /api/authority/kill`（1 回押すだけ、確認なし、いつでも使える。不健全のときも）、
`GET /api/authority/outbox[?unread=1]`、`POST /api/authority/outbox/ack {event_id}`。どれも
サーバーの Host / Origin / CSRF の検査の後ろにあり、モデルから見えるツールではない。イベント
のインカーネーションは短い `instance` の参照としてだけ見せる。**ラッチを解除するルートは
無い。**

## 運用の手順: キルと解除

1. **キル:** `POST /api/authority/kill`（ダッシュボード自身のオリジンから、その CSRF
   トークンで）。すべての許可証と `consume` がすぐに拒否され、YOLO は何も自動承認しない。
   取消がまだ走っている間は答えに `settlement: cancelling` が出る。`kill` ラッチが永続化
   される。
2. **見る:** `GET /api/authority/status` / `GET /api/authority/outbox`、またはホストで
   `stira authority status`（読み取りのみ。サーバーが動いていても使える）。
3. **解除**（サーバーを止めて。コマンドはデータディレクトリの `server.lock` を取り、
   サーバーが動いている間は拒否する）: `stira authority unlatch kill`（または `unhealthy`、
   `halted:<理由>`、`all`）。ラッチと停止のエポックを表示し、TTY と `UNLATCH` の入力が
   要り、表示したものだけを解除する: 間に変化があれば `resume_stale`（何も解除しない）。
   操作はこのコマンドのインカーネーション、停止 ID、ストアの世代に結びつき、同じ操作 ID が
   2 回適用されることはない。解除はそれぞれ記録される（`human_unlatch`）。
4. サーバーを**起動**し直す。

**修理**（いつもサーバーを止めて）:

* *使えない・無い・巻き戻されたラッチストア*: `stira authority reset-latches`（TTY、
  `RESET` の入力、`server.lock` を取る）。古いファイルは残し
  （`authority-latches.replaced-<hex>`）、**すべての**ラッチを立てた新しいストアを書き、
  そのコミットメントをエポックのファイルに、ラッチごとに `latch_store_reset` のイベントを
  記録する。その後、上の `stira authority unlatch …` で解除する。ファイルを消しても何も
  外れない: 次の起動が無いストアを拒否する。
* *途中で切れた・壊れたライフサイクルのログ*（追記中のクラッシュによる `lifecycle_log_torn`
  など `lifecycle_log_*`）: `authority-lifecycle*.jsonl` の写しを取る。切れた末尾なら、
  最後の完全な行（最後の `\n`）の後ろを切り取る。それ以外は両方の区切りを脇へ移す（鎖は
  始まりから始まらなければならない）。サーバーを起動し、（また止めて）
  `stira authority unlatch unhealthy`。脇へ移したイベントはログから消えるが、それが記録
  するラッチはラッチストアとそのコミットメントに残っている。
* *安全でない・使えないキルの印*（`kill_marker_unsafe` / `kill_marker_unavailable`。その
  間 `unlatch` は拒否する）: サーバーを止め、`authority-kill-armed` / `authority-kill-fired`
  を見る。おかしな *armed* のエントリ（シンボリックリンク、ハードリンク、FIFO、ディレクトリ、
  別の所有者、`0600` より広い）は消す（ディレクトリは `rmdir`。リンク先は決して消さない）
  ——次の起動が作り直す。おかしな *fired* のエントリはキルが押されたこと: キルのラッチは
  そのままにし、そのエントリだけを消して空の `0600` のファイルに置き換え、
  `stira authority unlatch kill` で解除する。その後 `stira authority unlatch unhealthy`、
  起動。
* *エポックのファイル*（エポックのファイル自体が壊れたときだけ。ラッチストアの修理には
  決して使わない）: 写しを取り、消し、`stira authority reset-latches`、起動、解除。
  `unlatch` 自身も約束されたものでないラッチストアを拒否し（サーバーと同じ検査）、そのとき
  は何も書かない。`reset-latches` はコミットメントが無傷のままで動く。

ラッチはひとりでには外れない: 再起動でも、時間でも、ブレーカーが NORMAL に戻っても。解除は
何も開かない: 次の起動が普通に動けるようにするだけ。

## 既知の制限（W4.5）

どれも閉じる側に倒れる（止まる / 不健全 / `clean` にならない）。権限に戻る道ではない。
残る項目は #618 で追う。

* **キルが耐久的になるのは `status()` が `kill_durable: true` を示してから。** `status()` は
  プロセス内の見え方で、`GET /api/authority/status` には `kill_durable` が無い。外からは、その
  `latches` に `"kill"` があり、**かつ** `latch_store_healthy` が `true` であることを確かめる
  （ラッチストアのメモリは書込が成功してから変わる。使えないストアはすべてのラッチを
  `latch_store_healthy: false` で並べるので、何の証明にもならない）か、ホストで
  `stira authority status` を実行する（ファイルを読む）。
  `latch: pending`（永続化のスレッドを始められず、ウォッチドッグが書く）、`timeout`（ハング
  したディスク）、`failed` と答えたキルは、フラグをメモリに立てただけ。書込が載る**前**の
  再起動は、発火した印かライフサイクルのログのキルのイベントがディスクに届いていなければ、
  健全で止まっていない状態で始まりうる。この窓は完全には閉じられない（どの設計にも永続化の
  前に落ちる瞬間がある）。再起動の後に status がキルを示さなければ、もう一度キルを押す。
* 渡された書込はウォッチドッグのスレッドで走る: ハングしたディスクはその一巡を止める（一巡
  自身の書込と同じ）。ウォッチドッグが動いていなければ（`watchdog_unavailable`）このプロセス
  では書かれず、`kill_durable` は false のまま。
* キルのコールバックは永続化の試みの後（ハングしたディスクでは最大 5 秒）に始まり、1 つずつ
  走り、それぞれ最大 `CANCEL_DEADLINE_SEC` 待つ（遅れだけ。#618 K3）。キルの要求そのものは、
  取消を出した後もエポックの I/O を待ちうる（#618 K5、可用性だけ）。
* キルのときに持ち主が走らせているバッチはその持ち主に残る（そこでコールバックがハングすれば
  `rescue_overdue` が残りを積み直す）。
* コールバックをキルの実行器に移した積まれたバッチはエポックだけを残す: それらのコールバックが
  終わる前に、前線とエポックファイルがそのバッチを越えうる（キル自身のバッチと同じ。#618 D2）。
  その間 `settlement` は `cancelling` のままで、`flush` は `clean` にならない（`_kill_pending`）。

## ここに無いもの（後の段階）

スケジューラの無条件の保守的な起動と停止 ID に結びつくトークン（W3）。ゴールループ（W5 以降）。
**W4（グラント、実行なし）**はこのサービスを次のように使う（[grants](grants_ja.md)）: グラントの
停止はどれもエポックを進める（`narrow("grant_stop")`、他のロックの下では遅延）。ウォッチドッグの
一巡でグラントのモデルを使わない確認を行う（`Watchdog(looks=…)`: キル・不健全・ブレーカー・時計・
TTL の期限・グラントストア）。グラントとゴールの遷移は主体 `grant` / `goal`（グラント ID）と
`grants` / `store`（その健全性）のライフサイクルイベントで、停止は `stop|grant|*|<理由>` の
停止通知になる。グラントは `halted:*` ラッチを立てない（グラントは再起動を越えない）。
ダッシュボードのキルボタンはグラントの節にある（ステージ C がオンのとき）。ADR 0011 §13 を参照。
