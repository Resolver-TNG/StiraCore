# コンテキスト管理（要点・日本語）

全体の説明・しきい値・計測は英語版 [context-management.md](context-management.md) と
[ADR 0005](adr/0005-context-management.md) にあります。ここは運用で必要な要点と、
#746 で変わった点の日本語版です。

## 何をするか

- 既定は OFF。`"context_management": true`（gateway 設定）または
  `STIRA_CONTEXT_MANAGEMENT=1` で有効にする（起動時に読む）。
- 大きなツール結果（既定 1,500 トークン超）を、マスク済みの原文として退避領域に
  移し、履歴には先頭のプレビューと参照だけを残す。読み戻しツールで参照できる。
- 入力がコンテキスト窓の `compression_threshold`（既定 0.85）に達すると、古い
  メッセージを要約に置き換える。

## 退避領域（stash）の場所

- `<context_stash_dir>/<agent_id>/offloader/<toolUseId>_<n>`。チャットサーバーは
  `<データディレクトリ>/context-stash/` を使う。ディレクトリは 0700 で作る。
- identity floor の上には置けない。そのうえで、エージェントの書込み root の中
  （#243）か、チャットサーバー自身の `<データディレクトリ>/context-stash/`（#746）の
  どちらかである必要がある。
- 退避はサーバー自身が書く（ファイルツール経由ではない）。そのため
  `workspace_dir` をデータディレクトリの外のプロジェクトに向けていても働く。
  書込み root には**追加されない**ので、ファイルツールはそこへ書けないまま。
- `context-stash/` が実ディレクトリのときだけ有効（シンボリックリンクはたどらない）。
  その下のエージェント用ディレクトリ（`context-stash/<agent_id>`）が別の場所への
  シンボリックリンクのときも拒否する（`stash_outside_write_roots`）。
- 書く前に秘密をマスクする（#185）。

## 制限と既知の穴

- 参照キー: `..` を含むキーとバックスラッシュを含むキーは拒否する。絶対パスのキーは
  退避領域からの相対として扱うので、外のファイルは指せない。保持期間の削除と
  `purge()` はシンボリックリンクを数えず、リンク先を消さない。
- 既知の穴: 退避領域の**中**に置かれたシンボリックリンクはたどる。読み戻しツールは
  リンク先のファイルを返し、リンクされたサブディレクトリの下への書込みはリンク先に
  書かれる。そのようなリンクを作るには退避ディレクトリ自体への書込み権限が要る
  （チャットサーバーでは、エージェントのファイルツールはそこへ書けない）。
- 既知の穴: プレビューと読み戻した本文は保存したとおりに返す。本文中の
  `<system-reminder>` / `<recalled-memory>` に似せた文字列は無害化しない（ツール結果は
  書き換えない）。モデルに届くのはツール結果の中だけで、プロンプトキャッシュが ON の
  ときも、本物のブロックはリクエストの最後の 1 つだけ。
- 承認待ちで止まった呼び出しは、再起動後もチェックポイントから再開できる
  （コンテキスト管理が ON でも同じ）。承認した呼び出しは 1 回だけ実行され、その結果で
  履歴がしきい値を超えたときは、次のモデル呼び出しの前に要約する。その呼び出しと結果は
  原文のまま残る。
- 上の 2 つの穴は `tests/test_context_management_gaps.py` に strict xfail で固定してある
  （直すとテストが赤になり、印を外す）。

## 拒否（`refused`）と理由コード

有効にしたのに条件を満たさないと `refused` になり、履歴は従来どおり扱われる
（退避も要約もしない）。サーバーログに、理由コードと直し方を含む警告が理由ごとに
1 回出る（パス・エージェント ID・例外文は含まない）。

| コード | 意味 | 直し方 |
|---|---|---|
| `no_stash_dir` | 退避ディレクトリが渡されていない | `context_stash_dir` を渡す |
| `agent_id_not_plain` | エージェント ID が単純な名前でない | 英数字と `_ . -` だけにする |
| `stash_outside_write_roots` | floor の上、または書込み root の中でもサーバーの `context-stash/` でもない | `<データディレクトリ>/context-stash/`（実ディレクトリ）か書込み root の中を使う |
| `stash_unusable` | ディレクトリを作れない・書けない | 存在と権限を確かめる |

- `agent.context_refusal_reason`: `refused` の間は上のコード、それ以外は `None`。
- `stiracore.agent.context_management.status_view(agent)`: `enabled`・`mode`・
  `reason` を許可リストの値だけで返す（状態表示用）。
- `turn.completed` の `context`（#746。機能がオフの間は付かない）: `mode`、`reason`
  （`refused` の間のコード）、`summaries`・`offloaded_results`（ターン後の履歴にある数）、
  `summarized_messages`（このターンで置き換えた数）、`history_messages`、
  `max_input_tokens`（このターンのモデル呼び出し 1 回の最大入力）。モード・コード・数値だけ。
- チャット画面（#746）: `refused` で終わったターンのあと、コンテキストゲージの下に
  「コンテキスト管理は有効ですが動いていません」と、理由コードを言葉にした文と直し方が
  出る（「⚠」の記号と文。日本語・英語）。`/api/gateway/status` の `context_management`
  を読む。4 つのコード以外の理由は「不明」と表示する。`refused` でないターンのあとに消える。

## ローカルサーバーの窓を使う（#746）

窓が設定にもモデルにも能力表にも無く、プロバイダーが `openai` / `openai_responses` で
`base_url` がローカル（ループバックか RFC 1918。#745 の出力上限と同じく URL の文字だけで
判定）のとき、サーバーに 1 回たずねる: `GET <base_url>/models` の、設定したモデル
（または一覧に 1 つだけあるモデル）の `meta.n_ctx`。llama.cpp 系のサーバーが返す。
このとき出所は `server`。返さなければ 200,000（`default`）のまま。

- たずねるのはコンテキスト管理が ON のターンだけ。API キーは送らない。プロキシは使わず、
  リダイレクトは追わない。待つのは 2 秒、答え（「返さなかった」も含む）は 5 分保持する。
  `/models` にキーが要るサーバーや `n_ctx` を返さないサーバーでは既定のままなので、
  `context_window_tokens` を設定する。
- 答えから使うのは正の整数 1 つだけ。ログには何も書かない。
- ホスト型のエンドポイントと `ollama` / `llamacpp` プロバイダーにはたずねない。

## 長時間の無人作業（#746）

ローカルモデルでの 24 時間の試行では、1 ターンの中で入力が約 6.6 k トークンから
55〜130 k（窓は 131 k）まで増え、機能が `refused` だったため一度も要約されなかった
（作業ディレクトリを移していたため。この場合は現在 `on` になる）。

- コンテキスト管理を明示的に ON にする。最初のターンの後、
  `/api/gateway/status` → `context_management.mode` が `on` であることを確かめる。
  `refused` ならサーバーログの
  `context_management is enabled but refused (<コード>)` の行を見る。
- `context_window_tokens` をサーバーの実際の窓（ローカルサーバーの `n_ctx`）に
  合わせる。未設定で未知のモデルは 200,000 になり、131 k の窓ではしきい値が窓を超える
  （ローカルサーバーが窓を返す場合を除く。上の節）。
- タスクごとに新しいチャットセッションを始め、残すべき状態は作業ディレクトリの
  メモファイルに書く。要約が残すのは識別子と未完了の項目で、細部すべてではない。
- ツールループの中では、前回の呼び出しでプロバイダーが報告した入力トークン数で
  要約が発動する。手元の見積もりが低くても、しきい値を超えたループは次の呼び出しの
  前に要約される。
- 見る数字は 3 つ: 1 回の呼び出しの最大入力（`context_tokens`。各呼び出しは
  `turns.db` の `model.completed`。ターン内の最大は
  `turn.completed.context.max_input_tokens`）、ターンあたりの要約回数
  （`last_context_management.summaries`。`turn.completed.context` にも入る）、そしてモード。
