# Neural State saturation and recovery — operator guide (#165)

日本語: [neural-saturation_ja.md](neural-saturation_ja.md). Measurements:
research/neural-saturation-2026-10-16.md
(generated by `scripts/saturation_report.py`, checked by `tests/test_saturation_report.py`).

In a long, one-sided conversation the Neural State runs to its bounds: stability near 0,
vigilance near 1, attachment pinned at 1.0, and the breaker at CRITICAL for most turns.
**This is an intended property of the engine, not a bug**, and the coefficients stay as
they are. This page explains why it happens, how long recovery takes, and which settings
an operator has to shape it. Memory housekeeping is a separate topic (#317).

## 1. Why the state saturates

Two rules move every dimension (code: `core/neural_state.py`, unchanged):

| When | Rule |
| --- | --- |
| A turn with a classified stimulus (`post_turn`) | `x ← clamp(x + EMOTION_MATRIX[stimulus][x] × intensity, 0, 1)` |
| Elapsed time (`pre_turn` of the next turn, or a heartbeat tick) | `x` moves linearly towards its baseline: `rate × hours` from above, `0.5 × rate × hours` from below, never past the baseline |

Measured for stability (intensity 1.0; full table in the research report, section 1):

| stimulus | stability per turn | idle time that undoes it |
| --- | ---: | ---: |
| achievement | +0.030 | 6 h |
| joy / connection | +0.020 | 4 h |
| uncertainty | −0.010 | 4 h |
| threat | −0.020 | 8 h |
| loss | −0.030 | 12 h |

So one turn is small, and decay needs hours to undo it. A short conversation never reaches
the breaker ([breaker-reachability.md](breaker-reachability.md)); a long conversation in
one direction accumulates faster than decay can return it, until the clamp at 0 or 1.

## 2. How long recovery takes (measured)

Live-probe classifier output (`sokudan-ja-310m`), default settings:

| Situation | Result |
| --- | --- |
| 120 hostile turns, 1 min apart | stability 0.015, vigilance 0.985, attachment 1.000; first CRITICAL at turn 63 |
| 240 hostile turns, 1 min apart | 178 of 240 turns end at CRITICAL |
| Same 240 turns, 3 h apart | stability 0.697, never CRITICAL |
| Positive turns after saturation | leave CRITICAL after 29–31 turns, WARNING released after 38–42 |
| Idle after saturation (no turns) | +6 h: 0.030 (CRITICAL); leaves CRITICAL after about 174 h (7 days); NORMAL after about 234 h (10 days) |
| Idle from 0.45 (WARNING) | NORMAL after 60 h |
| Idle from 0.25 (CRITICAL, cooldown served) | leaves CRITICAL after 80 h, NORMAL after 140 h |

CRITICAL needs its protected turns (`critical_cooldown_turns`, at least 3) before time can
lift it; heartbeat ticks never serve them ([heartbeat-daemon.md](heartbeat-daemon.md)).

## 3. What an operator controls

How flat the state stays is decided by **how the agent is used** and **the operator's
settings**, not by changing coefficients.

| Lever | Effect on the state | Where |
| --- | --- | --- |
| Turn gap (usage pattern) | **The largest effect.** Decay between turns is proportional to the gap: hostile input saturates at 1–60 min per turn, stays near the baseline at 3 h per turn. | how the agent is deployed |
| Heartbeat on/off | Applies decay and re-evaluates the breaker **without a user turn**, so an idle agent's release becomes visible (status, `/schedules`, scheduler gating) when it happens instead of at the next turn. | `gateway-config.json` `hb_enabled` or `STIRA_HEARTBEAT=1` |
| `hb_interval_floor_sec` / `hb_interval_ceil_sec` | Tick spacing `clamp(ceil × stability², floor, ceil)`. **Does not change the recovery curve**: decay is linear in time, so 5-minute ticks, 3-hour ticks and no heartbeat give the same stability at the same moment. The interval only sets how late (at most one interval) a release is applied and shown, and how many ticks run (400 h: 4800 at 5 min, 134 at 3 h). | `gateway-config.json` |
| Scheduler | **Does not touch the Neural State.** It is gated by it: create/update/resume refused at WARNING and above, nothing starts at CRITICAL. A `health_check` job reports `breaker=…, heartbeat=…` and raises `heartbeat_stalled`, so it is the way to *watch* the state on a schedule. | `STIRA_SCHEDULER=1`, [scheduler.md](scheduler.md) |
| Breaker thresholds | Move where WARNING / CRITICAL / COHERENCE start (the exit thresholds stay; an entry at or above its exit is refused). This changes when restrictions apply, not the state itself. | settings page (`stability_warning`, `stability_critical`, `bc_threshold`) |
| Manual reset | Stop the server and move `neural-state.json` aside: the state restarts at the baselines. A deliberate human action, never automatic. | [configuration.md §6](configuration.md) |
| Coefficients (`EMOTION_MATRIX`, `DECAY_RATES`, baselines) | Not configuration. Unchanged by design; they fix the per-turn change and the speed of idle recovery. | — |

### Examples

Always-on assistant, release shown within about 30 minutes of idle time (ticks are
model-free: no tokens, about 0.003 ms each):

```json
{"hb_enabled": true, "hb_interval_floor_sec": 300, "hb_interval_ceil_sec": 1800}
```

Default pacing (shorter ticks when stability is low, about 88 min at the baseline):

```json
{"hb_enabled": true, "hb_interval_floor_sec": 300, "hb_interval_ceil_sec": 10800}
```

Heartbeat off (the default): the same decay is applied at the next turn's `pre_turn`;
nothing changes while nobody talks to the agent.

Watching the state hourly (needs `STIRA_SCHEDULER=1`; a human creates the job with
`"confirm": true`):

```json
{"name": "hourly health", "action": "health_check",
 "schedule": {"type": "cron", "expr": "0 * * * *", "timezone": "Asia/Tokyo"}}
```

### Things to know

- **A release by time is not an approval.** It does not resolve or create approvals; tool
  rules and HITL still apply at every level.
- **After a long idle release the next turn shows COHERENCE**: ticks do not sample
  `bc_window`, so the first turn sees a jump in stability. COHERENCE only re-injects the
  identity anchors; it does not limit tools.
- **Positive conversation releases much faster than idle time** (about 30 turns vs about
  7 days from the saturated state).

## 4. Breaker log (#165)

- A level change is logged once, in full (`🚨 CRITICAL: stability=…`, `⚠️ WARNING: …`,
  `🟢 NORMAL: …`).
- While a non-NORMAL level persists, a one-line summary is logged every 20 consecutive
  turns (`breaker CRITICAL continues: turns=20 stability=0.00 bcScore=0.66`); the other
  turns are logged at DEBUG. The period is the `StiraEngine(breaker_log_every_turns=…)`
  argument (default `BREAKER_LOG_EVERY_TURNS = 20`).
- The lines carry the level, numbers and fixed text only — never conversation text or the
  emotion transcription (`tests/test_breaker_log_throttle.py`).
- The `on_breaker` callback is **not** throttled: it still fires on every transition and
  on every CRITICAL turn, because hosts re-apply tool restrictions from it.

## 5. Design memo: attachment soft clip (not implemented)

**Observation.** In 240 hostile turns at 1 min, attachment ended 124 turns pinned at 1.0
and the clamp discarded 1.33 of positive attachment change. Once pinned, more pressure and
less pressure look the same; that information is lost.

**Option (proposed, off by default).** A soft clip applied only to positive changes of
selected dimensions: `Δ' = Δ × (1 − x) / (1 − knee)` while `x > knee`, so changes shrink as the
dimension nears 1.0 instead of being cut off there. Constraints: off by default with today's behaviour
bit-for-bit; `EMOTION_MATRIX`, decay, baselines, `NeuralState` fields, `version` and
`schema_version` unchanged; no Layer 3 change; one opt-in config key with validation and
tests; the reachability and saturation reports regenerated with the option off (no diff)
and on (new tables).

**Why not in this change.** It touches `apply_stimulus`, the core of the regularisation
term, and needs decisions that are not about logging or documentation: which dimensions,
the curve, whether negative changes near 0 are softened too, and whether the breaker
should see the clipped value. It is left for a separate issue.

## 6. When the state does not move: which classifier runs, and why (#367)

The opposite of saturation: a conversation in which the emotions barely move. The usual
cause is the classifier, not the coefficients. With the default choice `auto`, the server
uses Sokudan when the optional `sokudan` package is installed and the rule detector
(`RuleBasedClassifier`) otherwise. The rule detector fires on a few fixed patterns only
(gratitude, greeting, question, long reply, tool error/success, breaker level), so many
turns get **no stimulus** and leave Neural State unchanged. A live run measured 7 of 19
turns with a change on the rule fallback.

Where it shows (display only; the classifier, its thresholds, EMOTION_MATRIX and
NeuralState are not changed):

| Where | What |
|---|---|
| Start-up log | One line, `WARNING: emotion classification is rule-only: sokudan is not installed (pip install -e ".[jev]" …)`, when the choice is `auto` or `sokudan` and the package cannot be found. Not printed for an explicit `rule` choice. |
| `/api/gateway/status` → `classifier` | Added: `mode` = `rule_only` / `sokudan` / `unknown` (unknown = not resolved yet — `auto` resolves on the first turn — or a third-party classifier); `fallback` = `true` when rules run although Sokudan was asked for (`auto` / `sokudan`), `false` otherwise, `null` while unresolved. `name` / `is_jev` / `model` are unchanged. |
| `/api/gateway/status` → `emotion_updates` | Turns since start-up: `turns`, `updated`, `not_updated`, `reasons` (count per code below) and `last` (`{"updated": bool, "reason": code \| null}`, `null` before the first turn). Codes are a fixed allow-list; anything else reads `unknown`. |
| Chat page, Gateway card | Stimulus classifier: `⚪ rules only (fallback)` with the install hint as its title. Emotion updates: `changed in 7 of 19 turns · last: no stimulus detected`; the title has the per-reason breakdown. |
| Turn ribbon / inspector | A turn whose deltas are empty reads `No change` (it used to read `No stimulus`): the turn summary does not carry the reason, so the ribbon states only the fact and the Gateway card gives the reason of the last turn. |

"No update" reasons (`NO_UPDATE_REASONS`, `agent.last_turn_summary["no_update_reason"]`):

| Code | Meaning |
|---|---|
| `no_stimulus` | The classifier abstained (no rule fired, or Sokudan below its confidence threshold). |
| `classifier_error` | The classifier raised; the turn continues as if it abstained (logged as `Stimulus detection failed`). |
| `unknown_stimulus` | The classifier named a category outside EMOTION_MATRIX; it is ignored. |
| `no_change` | A known stimulus moved no value: intensity 0, or every affected value already at its limit (see §1). |
| `turn_incomplete` | The turn did not complete (model error, cancel); the classifier is not asked. |

To add Sokudan: `pip install -e ".[jev]"` in a Python 3.11 environment and restart the
server. The settings page (`/settings`, emotion classification) shows the saved choice and
what it resolves to (`GET /api/config/jev`). The classifier is resolved once at start-up
(#227): a choice saved while the server runs is pending until the restart, and until then
`mode` / `fallback` keep describing the classifier that runs (the start-up choice).
