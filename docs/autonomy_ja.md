# 自律（アルファ版）: 概要・使い方・既知の制約

[English](autonomy.md) | 日本語

> **アルファ版 — 実験的で、既定はオフ。** このページの内容は予告なく変わることがあります。
> 失って困るものの上で、見張りなしに動かしたままにしないでください。これは
> [ADR 0011](adr/0011-agent-self-scheduling.md) の grant 付きゴールループ（「ステージ C」）で、
> #296 で追跡しています。このページは概要です。詳しい規則は [grants_ja](grants_ja.md)、
> [authority-service_ja](authority-service_ja.md)、[stage](stage.md) にあります。

**ひとことで。** 人が **1 つの目標**に対して**グラント**を発行します: 時間の上限、トークン予算、
反復の上限、使ってよいツールの範囲、作業ディレクトリ 1 つ。発行しただけでは何も動きません。
目標の各**反復**はチャットとは別の専用セッション（`grant:<id>`）で動きます。動くのは、人が
**1 反復だけ実行** を押したとき、または — サーバーとそのグラントの両方が許しているときだけ —
スケジューラーのハートビートの確認が 1 反復を始めたときです。エージェントは進捗の報告、行き詰まりの
報告、目標を達成したという*申告*ができますが、**完了にできるのは人だけ**です。絞り込み（キルスイッチ、
取り消し、ブレーカーが NORMAL を外れる、`/new`、TTL、再起動）があれば止まります。

## 2. 試し方（手順）

捨ててよい作業ディレクトリを使ってください。ラベルは日本語 UI のもの
（`dashboard/static/i18n/catalog.ja.json`）です。英語 UI でも同じ項目が出ます。

1. **ホストでの確認（既定）。** 発行・再開・確認は**ホストで**確認する必要があります:
   `STIRA_YOLO_HOST_CONFIRM=auto`（macOS では OS の認証付きデスクトップダイアログ）、`dialog`、
   `command`（TTY で `stira approvals decide <short>` で確認。`auto` は macOS のデスクトップの
   セッションの外ではコマンドになる）のいずれかを設定し、YOLO の許可
   （`STIRA_YOLO_ALLOW`、既定 `external`。`off` にすると経路が無くなる）を残します。ホストの経路には
   POSIX のホストが要ります（Windows では使えません）。ホストの経路が無ければこれらの操作は拒否
   されます（`host_channel_required`）。弱い層であるブラウザでの確認は
   `"allow_browser_confirm": true` **かつ**ホストの経路が設定されていないときだけ受け付けます（手順 4。
   [制約](#4-既知の制約) を参照）。
2. **スイッチ。** `.local/stira/gateway-config.json`（起動時に読む。手での編集のみ）に:

   ```json
   {"autonomy": {"stage_c": true, "stage_c_exec": true}}
   ```

   `stage_c` だけなら操作面（発行・停止・確認）だけで、何も動きません。`stage_c_exec` で実行部と
   **1 反復だけ実行** ボタンが加わります。サーバーを再起動します。全キー:
   [configuration_ja](configuration_ja.md)「`autonomy` セクション」。

   **ハートビートで始める（任意。次のすべてが要る）:** (a) 同じ `autonomy` 節に
   `"heartbeat_start": true`（`stage_c_exec` が要る）。(b) スケジューラーをオン、`STIRA_SCHEDULER=1`。
   (c) ハートビートのデーモンをオン — gateway の `hb_enabled: true` か `STIRA_HEARTBEAT=1`（既定オフ）。
   `STIRA_HEARTBEAT=0` は `hb_enabled: true` より優先される。(d) 再起動し、サーバーのコンソール
   （stderr。logging の警告）に `grants: heartbeat_start unavailable (reason=scheduler_off | heartbeat_off)`
   の行が無いことを確かめる — これは起動時に 1 回だけ決まり、あとでハートビートが止まれば、グラントの
   カードに `heartbeat_unhealthy` の見送りとして出る。(e) グラントを **ハートビートで反復を始めてよい** にチェックして発行する
   （手順 4）。スケジューラーが無ければティッカーを起こすものが無く、ハートビートが無ければ起床は
   すべて見送られ（`heartbeat_unhealthy`）、グラントのフラグが無ければ tick がそのグラントを始めることは
   ありません。

   **ハートビートで始める反復のツールのルール。** `editor` と `run_checks` の既定は **毎回確認** で、
   ハートビートで始めた反復ではだれもカードに答えません: 最初の書き込みで `approval_timeout` に
   なって終わります（目標は行き詰まり、グラントは一時停止。スモークでは 1.3 秒、約 2.7k トークン）。
   無人で動かすなら先に設定ページで **常に許可** にします:
   1. 設定 › 安全 › **ツールの許可**（`/settings#sec-tools`）で `editor`（と `run_checks`）を
      **常に許可** にします。選んだだけではまだ何も送りません。
   2. （ページ下の）**保存** を押します。
   3. 「安全性が下がる変更です」のダイアログが開きます: `許可する` と入力し（「続けるには「許可する」と
      入力してください」）、**さらに**ツール名を入力して（「「常に許可」にするツール名を入力: editor」。
      2 つなら `editor run_checks`）、**理解したうえで保存** を押します（両方が合うまで押せない）。
   4. YOLO の許可がオン（既定）なら、保存はホストで確認する `rules_loosen` の操作です: ブラウザの経路
      なら 2 つめのダイアログが開くので「内容を確認しました(いま自分が押した操作です)」にチェックして
      **確認して適用** を押します。`STIRA_YOLO_HOST_CONFIRM=command` / `dialog` ならページに確認の場所が
      出ます — サーバーのコンピューターの端末で表示された `stira approvals decide <short>` を実行する
      （照合コードを確かめて入力する）か、デスクトップのダイアログで確認します。そこで初めてルールが
      保存されます。

   API からは（1 回に 1 ツール）: `POST /api/config/tools {"name": "editor", "policy": "always",
   "confirm": true, "confirm_always": ["editor"]}`（`confirm` かツール名が無ければ 400）が 428
   `host_confirmation_required` と `rules_loosen` の操作（`operation.id`・`short`・`channel`、コマンドの
   経路なら `command`）を返します。上と同じくホストで確認する（`stira approvals decide <short>`）か、
   ブラウザの経路ならダッシュボードのページから `POST /api/host-operations/<操作 id>/confirm` で確認し、
   同じ要求を `X-Stira-Host-Operation: <操作 id>` 付きでもう一度送ります。ブレーカーが NORMAL でない
   間はどのルールも緩められません。`run_checks` に保存した「常に許可」が効くのは、検証済みの
   `os_sandbox` のホストだけです（ほかでは「毎回確認」として読む）。押下で始める反復には「常に許可」は
   要りません: カードにあなたが答えます（手順 5）。

   **グラントに `run_checks` を含める（任意）:** ツールが登録されていること（gateway の
   `{"run_checks": {"phase": 1}}`、既定オフ。Windows と root では登録されない。`STIRA_RUN_CHECKS=0`
   で強制オフ）、
   `autonomy.run_checks_unattended` が `true`（既定）のままであること、ホストに検証済みの
   `os_sandbox` があること（macOS）。どれかが欠けると、ツールに `run_checks` を含むグラントは発行時に
   拒否されます（`grant_run_checks_setting_off` / `grant_run_checks_not_contained`）。あとで条件が
   下がれば目標は行き詰まりになります（`blocked(run_checks_unavailable)`）。**`run_checks` が選ぶ
   インタープリターから pytest を import できること:** 調べるフォルダーの `.venv`（または
   `venv`）、次にエージェントの作業フォルダー（`workspace_dir`）の同じもの、次にサーバー自身の Python
   です。そこに pytest を入れます（venv 自身の
   `site-packages`、または `--system-site-packages` で作った venv ならその元のインタープリター）。
   無ければモデルには `pytest_not_installed` が見え、たいてい `blocked(needs_decision)` を報告します。
   `--system-site-packages` で作った venv が元のインタープリターのパッケージを見るのは、その元が
   サーバー自身の元のインタープリターのときだけです。ほかの元は読みません（不明: pytest を出すのは
   フォルダーに pytest の設定（`pytest.ini`・`conftest.py`・`pyproject.toml` の `[tool.pytest.ini_options]`）があるときだけ）。有無はファイルで
   読むので、`.pth` のパスだけで入れた pytest（編集可能インストール）は見えません
   （`pytest_not_installed`）。`stira checks discover <フォルダー> --workspace <workspace_dir>` で
   見つけたものが分かります（何も実行しない。`--workspace` が無いとフォルダー自身を作業フォルダーと
   みなすので、作業フォルダーの venv は出ません）。W6-F より前は、
   `python` がサーバーの元のインタープリターへのシンボリックリンクである venv を、サーバー自身の
   パッケージで答えていました（#641）。
3. **プロバイダ。** 反復が動くのは **Amazon Bedrock** だけです（実行部が Bedrock のクライアントの
   最終要求を 1 つずつ守るため。テスト用の偽モデルは別）。ほかのプロバイダは拒否されます
   （`provider_unsupported`）。
4. **グラントを発行する。** 設定 → **目標グラント（ステージ C）**（`/settings#sec-grants`）→
   **新しいグラントを発行**: *目標*（秘密情報は書かない。マスク処理で変わる目標は保存されない）、
   *使ってよいツール*（`file_read`・`editor`・`run_checks`・`memory_read`・`memory_search`・
   `memory_list`・`current_time` の一部）、*作業ディレクトリ*（書込みルートの中の絶対パス）、
   *総トークン予算*（フォームの既定 2,000,000、上限 5,000,000）、*1 tick あたりの上限*（フォームの
   既定 200,000）、*有効時間*（分、フォームの既定 120、最大 360）、*最大反復*（既定 10、最大 20）、
   必要なら *ハートビートで反復を始めてよい*（ゲートウェイのスイッチがオンのときだけ出る。あとから
   変えられない）。`ISSUE` と入力して **発行** を押します。ホストの経路（既定）では、ページに
   「操作 <short> をホストで確認してください（stira approvals decide <short>、またはデスクトップの
   ダイアログ）。」と出て待つので、ホストで確認します。**ブラウザでの確認（弱い層、任意）:** 設定
   されたホストの経路が常に優先されます — `allow_browser_confirm` はブラウザでの確認を*許す*だけで、
   *選び*はしません。使うには、ブラウザの経路を選び（`STIRA_YOLO_HOST_CONFIRM` を未設定か
   `browser` にし、`yolo.host_confirm` を既定の `"browser"` のままにする。または YOLO の許可を
   オフ、`STIRA_YOLO_ALLOW=off` — **このとき `STIRA_YOLO_HOST_CONFIRM` と、ほかの `STIRA_YOLO_*` の
   上書き変数（`STIRA_YOLO_MAX_AUTO_APPROVALS`・`STIRA_YOLO_MAX_EXTERNAL`・`STIRA_YOLO_MAX_EXEC`）を
   すべて未設定にする**。残っているとサーバーは起動を拒否します: `STIRA_YOLO_HOST_CONFIRM is set but
   the YOLO allowance is off`）、`autonomy` に `"allow_browser_confirm": true` を入れて再起動します。
   すると **発行** でブラウザのダイアログが開き、**内容を確認しました** にチェックして **発行** を
   押します（ホストの手順はありません）。ブラウザの経路で `allow_browser_confirm` が無ければ、発行・
   再開・確認は拒否されます（`host_channel_required`）。グラントは `active` になりますが、まだ何も
   動きません。**API で使う場合:** スクリプトでの流れ（428 の応答、`POST
   /api/grants/operations/<op>/confirm`、`X-Stira-Host-Operation` 付きで同じ要求をもう一度）は
   [grants_ja](grants_ja.md)「人間の操作面」にあります。
5. **1 反復だけ実行。** グラントのカードの **1 反復だけ実行** を押します。反復は裏で動きます。
   承認が必要なツール呼び出しがあれば、**承認ページ** でカードが待つので、そこで
   答えます。答えないままのカードはエージェントの `hitl_timeout_sec`（既定 120 秒。反復自身の壁時計の
   上限より後にはならない）で期限が切れ、反復を終わらせ、目標を行き詰まりにします
   （`blocked(approval_timeout)`）。`editor` と `run_checks` が「毎回確認」なら、ふつうの反復は
   **3〜4 枚のカード**を求めます（editor の表示、書き込み、`run_checks` の実行。スモークで測定）。
   API のクライアントはカードの `args_hash` を付けて承認します（無いと 400 で拒否され、カードは期限まで
   待ちます）。
6. **ボードを読む。** Stage（`STIRA_STAGE=1`、`/stage/`）の **稼働状況** モードを開きます。
   「目標グラント」の欄に、状態、*反復 n / 最大*、残り時間と残り予算、最後の終わり方、直近 5 反復、
   案内（「あなたの承認待ちです」「達成の申告があります。あなたの確認待ちです。」）が出ます。表示
   だけで、操作は設定に残っています。設定のカードにも同じ内容と操作があります。
7. **申告と確認。** エージェントが目標を達成したと申告すると、目標は `awaiting_verification`（確認待ち）
   になり、カードにハーネスが測った証跡が出ます（「申告時のチェック」「作業ツリー」「申告した反復の
   進捗」、チェックが不合格なら「⚠」の行）。ファイルを自分で見てから **完了を確定** か **差し戻す**
   を押し、（手順 4 と同じく、ホストで）確認します。確定するとグラントは終わります（`ended(complete)`）。
   差し戻すと、目標の「進捗なし」の連続回数が 1 増えます（反復の回数は増えません）: その連続回数が
   グラントの `no_progress_ticks`（既定 3）に届かなければ目標は `active` に戻り、届けば目標は
   `blocked(no_progress)` になり、グラントもそれに合わせて一時停止します。モデルには差し戻しの
   **理由は伝わりません**（次の反復に理由は渡らない。#644）: スモークでは同じ証跡でもう一度申告し、
   差し戻し 2 回で `blocked(no_progress)` まであと 1 歩になりました。
8. **一時停止 / 再開 / 取り消し。** **一時停止** と **取り消す** は 1 回押すだけです。**再開** には
   ホストでの確認が要り、停止（ブレーカーが NORMAL を外れた）からの再開ではさらに `RESUME` の入力と、
   ブレーカーが NORMAL に戻っていることが要ります。取り消しは最終です。続けるには新しく発行します。
9. **キルスイッチ。** **キルスイッチ（すべて停止）** は、メモリの上ですべてのグラントを取り消し、
   新しい許可をすべてその場で拒否します（すでに動いている効果は終わるまで動き、記録されます）。
   動いている反復は取り消され、次の区切りで終わります。そのあと `kill` ラッチとして**永続化**され、
   サーバーを止めて人が解除するまで再起動しても止まったままになります — `stira authority unlatch
   kill`（TTY、`UNLATCH` と入力）— ただし**書き込みが届いてから**です。届いたときはキルの応答が
   `latch: set`（または `already_set`）で、その後の `GET /api/authority/status` では `latches` に
   `"kill"` があり `latch_store_healthy: true` になります（ホストで `stira authority status` でも確認
   できます）。`latch: pending`・`timeout`・`failed` と答えたキルは、それが出るまではメモリの上だけで、
   書き込みが届く前に再起動するとキルされていない状態で起動することがあります（既知の制限。再起動後に
   状態に出ていなければ、もう一度キルを押してください）。[authority-service_ja](authority-service_ja.md)「運用の手順: キルと解除」
   を参照。
10. **再起動。** 再起動のたびにすべてのグラントが取り消されます（`revoked(restart)`）。新しく発行します。

## 3. ハーネスが保証すること — と、保証しないこと

**保証すること（それぞれテストで固定。失敗は閉じる側。[§4](#4-既知の制約) の残余 — なにより最後の
命令の窓と同じユーザーのプロセス — を除く）:**

* 既定はオフで、ハートビートは二重にオフ: スイッチがオフならルートもスレッドもファイルも無く、API の
  応答もこれまでどおり。
* 人がホストでの確認つきで発行したグラントがなければ何も動かない（人が弱いブラウザの層を選んだ場合を
  除く）。生きているグラントはサーバーに最大 1 つ。
* TTL は既定 2 時間・上限 6 時間で、延長しない。反復は既定 10・上限 20。トークン予算（総量 ≤ 5,000,000、
  1 tick ≤ 総量）はリセットしない。収まらない要求は送らない。
* **効果ごとに許可を 1 つ**: モデル呼び出し・ツール呼び出し・承認待ち・報告のそれぞれが、権限エポックと
  グラントに束縛した許可を取り、I/O の直前にもう一度確かめる。絞り込み — キル、取り消し、一時停止、
  ブレーカーが NORMAL を外れる、`/new`、TTL、時計の異常、保存先の異常 — があれば次の効果は拒否される。
* **割り込み**: ターンロックを取るもの（なにより人のチャットのターン）があれば、動いている反復は次の
  区切りで譲り、ターンの間は反復を受け付けない。
* **承認に自動で答えるものは無い**: 押下で始めた反復では「毎回確認」に答えるのは人のカードだけ（YOLO も
  許可の持ち越しも無し）。無人（ハートビート）の反復は待たずに `approval_timeout` で終わり、目標を
  行き詰まりにする。
* ツールはグラントの範囲 ∩ 決まった読み取り / 編集 / チェックの一覧 ∩ 現在のルール（「使わない」は
  出ない）。shell・web・delegate・MCP・スケジューラーのツールは無い。editor は作業ディレクトリの中に
  閉じ込める（許可の前と、消費の後にもう一度確かめる）。
* `run_checks` は OS のサンドボックス（`os_sandbox`）が検証済みのホストでだけ、呼び出しのたびに
  確かめ直して動く。`limits_only` のホストではそれを含むグラントは拒否される。
* **目標を完了にできるのは人だけ。** 申告は目標を `awaiting_verification` にするだけ。証跡はハーネスが
  測ったコードで、モデルの文ではない。自動で確定も差し戻しもしない。
* 目標の文の行き先: **保存**されるのは `grants.json`（`0600`）とサーバーのメモリだけ。**表示**されるのは
  発行した本人に 1 回だけ（発行の応答の一度きりの閲覧トークンで `GET /api/grants/<id>/goal?confirm=SHOW`
  — 「目標を表示」）。**モデルには送られる**: 反復のモデル呼び出しのたびに、入力の最後（信頼済みの
  手順書の後の文脈ブロック）に入る。ログ、ライフサイクルイベント、アウトボックス、ほかの API の表示
  （`/api/grants`・`/api/activity`）、承認のデータベース、チェックポイント、チャットのセッション、Stage の
  ボードには届かず、そこにあるのは ID とコードだけ。
* 取り戻しは無い: 逃したハートビートの起床はやり直さない。再起動はすべてのグラントを終わらせる。

**保証しないこと:**

* 作業が正しい・役に立つこと。進捗の検出は「変わった」と「変わらない」を分けるだけで、「良くなった」は
  分からない。無関係な編集も新しい結果になる。判断するのはあなたの確認だけ。
* 作業ディレクトリの独占: スケジュールされたジョブ、ほかのプロセス、あなた自身が同時に書ける。
* 同じ OS ユーザーで動く別のプロセスからの保護（制約を参照）。
* 反復 1 回あたりの費用の上限。人が見守ったスモーク 1 回が幅を測っただけです（[§4](#4-既知の制約)）。
  実際の費用は目標・モデル・リポジトリで決まります。
* キルのラッチ以外の、永続する停止: グラントはメモリにあり、設計どおり再起動で終わる。
* 名前・ルート・設定・保存形式の安定（アルファ版）。

## 4. 既知の制約

[grants_ja](grants_ja.md)「既知の制限」、[authority-service_ja](authority-service_ja.md)「既知の制限（W4.5）」
と #296 のレビューから集めました。未解決の項目は #618・#620・#623・#636・#638 で追跡しています。
特に書いていない限り、どれも権限を広げず、閉じる側に失敗するか、表示 / 遅延の問題です。

* **最後の命令の窓。** HTTP 要求が出ていく前の最後の確認より後に来た停止（ハートビートの喪失、
  スケジューラーの停止、人のターン、TTL）は、その要求には見えません。次の区切りで
  見えます。受け入れた残余です（#638）。
* **記録を保存した直後の停止。** 申告の証跡を置いた直後に来た絞り込みは、その後の出来事として扱います:
  記録は置いた時点で正しかった内容を保ちます。ロックを取らないキル / ターンの読み取りと保存の間の
  最後の一瞬に来た停止は、その後として扱います（W1 の囲われたコミットと同じ、受け入れた一瞬）。
* **ハートビートは開始の条件だけ。** 反復の最初の要求の後は、ハートビートを失っても止まりません
  （ほかの停止は効きます）。
* **送信済みの呼び出しは中断しない。** すでに送ったプロバイダの呼び出しや、動いている `run_checks` /
  `editor` の呼び出しは終わるまで動きます。停止の後、反復は動いているモデル呼び出しを待ちます（0.5 秒、
  応答を読んでいる間はさらに最大 5 秒。終了処理と壁時計の上限では待たない）: 終わった呼び出しは報告
  された使用量で計上します（W6-F、#640）。それでも動いている呼び出しは*放棄*されます（プロバイダの要求に
  止まるよう伝え、答えは捨て、**予約は全額**請求したまま、それが生きている間は新しい反復を受け付けない
  — 長さを縛るのはクライアント自身のタイムアウトだけ）。
* **ループ検出の限界。** **256 を超えるファイル**にまたがる循環は、検出を保証しません（古いパスは指紋から
  外れる）。**64 MiB を超えるファイル**はサイズと 3 MiB の抜き取りで識別するので、抜き取りの外の同じ
  サイズの変更は見えません。1 反復で読むのは最大 256 MiB（超えると不明、進捗なし）。
* **同じユーザーのプロセスは範囲外。** 同じ OS ユーザーの別のプロセスは `grants.json`、設定、作業
  ディレクトリを編集できます（たとえば最後の確認と書き込みの間にディレクトリの名前を変える）。
  ダッシュボードの CSRF / Origin の確認は、同じユーザーの API クライアントと人を区別できません —
  「1 反復だけ実行」、カードの承認、設定の編集を含むすべてのルートで同じです。
* **ホストでの確認とブラウザでの確認。** `allow_browser_confirm: true` では、同じユーザーのプロセスが
  発行・再開・確認を操作できます（証明はすべて要求したブラウザに渡る）。ホストの経路のほうが強い層です。
  `heartbeat_start` 付きのグラントも、いまはブラウザの層で発行できます（#638）。
* **生きている承認カードは引数を見せる**（パスと内容を含む）。通常の承認待ちの表示で、ほかの承認カードと
  同じです。保存する記録はコードだけです。
* **プロンプトキャッシュなし**: 反復のモデル呼び出しはキャッシュを使いません。信頼済みの文脈ブロックは
  Stira の見積もりで呼び出しごとに約 355 トークン（トークナイザーで測った値ではない）、目標がさらに
  最大約 500。W6e のスモーク（Bedrock の Sonnet 5.5 で人が見守った 1 回の実行、2026-10-26。見積もりで、請求額ではない）では、どの呼び出しにもキャッシュの数
  （`cacheReadInputTokens` / `cacheWriteInputTokens`）が報告されませんでした（2 回目の反復も含めて）。
  反復の呼び出しの経路にキャッシュが無いので、すべての呼び出しがキャッシュなしの全量のプロンプトだったと
  読めます。反復の中では呼び出しのたびに履歴を送り直します
  （5 回呼んだ反復で入力は約 18.2k）。
* **費用はスモーク 1 回の見積もり。** W6e のスモーク（Bedrock の Sonnet 5.5 で人が見守った 1 回の実行、2026-10-26。見積もりで、請求額ではない）: ふつうの反復はモデルを
  1〜7 回呼び、**2.7k〜28k トークン**、**1.3〜24 秒**でした。各反復の最初の呼び出しは入力 2,619 /
  出力 68、トークンの約 96 % が入力。W6-F より前は、モデル呼び出しの最中の停止で予約の全額（約
  **71〜74k トークン**）を計上していました（使ったのは約 2.7k、#640）。予算の上限は保守的なままです
  （テストでは Stira の見積もりの約 4 倍）。
* **Bedrock だけ。** ほかのプロバイダは拒否されます（`provider_unsupported`）。
* **日次の予算プールは無い。** 効くのはグラントの総量と 1 tick の上限だけです。スケジューラーの日次
  プールはグラントと共有していません。
* **YOLO の二重束縛と taint の永続化は未実装**（W7 / W8）: 反復の中の自動承認は無く、反復の出力に
  taint やエピソードの出所は付きません。
* **`run_checks` には macOS が要る。** 検証済みの `os_sandbox` は macOS（`sandbox-exec`、自己テストに
  合格した後）にだけあります。Linux（`limits_only`）では `run_checks` を含むグラントは拒否され、
  Windows には `run_checks` がありません。
* **時計。** 壁時計がスリープを含む時計と 5 秒を超えてずれる（たとえば NTP のステップ）と、グラントは
  取り消されます（`clock_anomaly`）。スリープを含む別の時計が無いホストでは、スリープも飛びとして
  扱います。壁時計が前に飛ぶと、最初のハートビート開始が早まることがあります（#638）。
* **繰り返しの失敗の門。** `failed` と `no_action` の終わりが交互に来ると、ハートビートの繰り返し失敗の
  見送りをすり抜けます（進捗なしの規則は引き続き目標を行き詰まりにする、#638）。
* **キルが永続になるのはラッチが書かれてから**（プロセス内の `kill_durable: true`。外からは
  `GET /api/authority/status` の `latches` に `"kill"` があり `latch_store_healthy: true`）。
  ラッチの書き込みが届く前に落ちると、
  キルされていない状態で戻ることがあります。再起動後に状態に出ていなければ、もう一度キルを押して
  ください。
* **UI**: 設定のカードはポーリングのたびに作り直されます（#620）。
