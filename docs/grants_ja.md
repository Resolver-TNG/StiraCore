# 目標グラント（ADR 0011 ステージ C、W4 + W5 + W6a〜W6d）— アルファ版

**状態: アルファ版 — 予告なく変わることがあります。既定はオフ。** 概要・試し方の手順・集めた既知の
制約: [autonomy_ja](autonomy_ja.md)。このページは規則の全体です: データモデル・状態機械・人の操作面
（#296 の W4）、別のスイッチの後ろにある**目標の反復の実行部**（W5）、結果による進捗（W6a）、すべての
ターン保持者による割り込み（W6b）、申告の証跡（W6c）、ハートビートによる開始（W6d）。グラントは発行
しただけでは何も動かしません。`autonomy.stage_c_exec` がオンのとき、**人が「1 反復だけ実行」を押すと**
反復が **1 回だけ**動きます。さらに `autonomy.heartbeat_start` がオン**かつ**グラントが自分の
`heartbeat_start` フラグ付きで発行されていれば、スケジューラーのモデルを使わない `grant_tick` が、同じ
`step` を通って起床 1 回につき最大 1 反復を始められます（下の「ハートビート開始」）。**押下の中で自動の次の
反復は無く、モデルによるループの判定も無く（進展は反復が何を変えたかからハーネスが決める。W6a）、完了の
主張は毎回ユーザーが確認します。** すべて**既定でオフ**（gateway の `autonomy.stage_c`、その上で
`autonomy.stage_c_exec`、さらに `autonomy.heartbeat_start`）。English: [grants.md](grants.md)。

## これは何か

**グラント**は、人がダッシュボードで発行する、時間・予算・範囲を決めた許可です。その
**目標**が目的です（ADR 0011 §2, §8）。どちらも 1 つのレコードにあります:

| 項目 | 意味（v1） |
|---|---|
| `grant_id` | 32 桁のランダムな 16 進。再利用しない |
| `kind` | 常に `goal` — YOLO の窓（`kind="yolo"`）との判別子。目標グラントが窓として扱われることも、その逆もない |
| `session_ref` | `grant:<id>` — W5 の反復が動く専用セッション |
| `goal` | 自由記述。**グラントストアにだけ**保存（`grants.json`、`0600`）。`mask_secrets` で変わる目標は拒否。それ以外（ログ・ライフサイクルイベント・アウトボックス・一覧・エラー・監査）では `grant_id` だけで参照する |
| `scope.tools` | `file_read`・`editor`・`run_checks`・`memory_read`・`memory_search`・`memory_list`・`current_time` の空でない部分集合 |
| `scope.workspace_subtree` | エージェントの書込みルート内に実在するディレクトリ。解決済み（シンボリックリンクで外へ出ない）で、書込みの床の内側 |
| `budget` | `total_tokens`（≤ 5 000 000）と `per_tick_tokens`（≤ 総量） |
| `ttl_sec` | 既定 7200（2 時間）、上限 21600（6 時間）。延長しない |
| `max_iterations` | 既定 10、上限 20 |
| `no_progress_ticks` | 既定 3 |
| `verifier` | `user`（v1 ではこれだけ）。確認の無いグラントは発行できない |
| `issued_*` | 発行時の壁時計・スリープ込み・スリープ抜きの読み |
| `issuer` | `dashboard`（ホスト確認済み） |
| `claim_evidence` | W6c: 最後の完了の申告の証跡。ハーネスが測ったコードとカウンタだけで、モデルの文は入らない（[下](#完了の申告-証跡と確認待ちw6c)）。最初の申告までは `null` |

**範囲に `run_checks` を含める**には、ユーザー設定 `autonomy.run_checks_unattended`（既定
true）**と**、検証済みの `os_sandbox` ホスト（ADR 0019）の両方が要ります。`limits_only` の
ホストでは、設定に関係なく `run_checks` を含むグラントは拒否されます
（`grant_run_checks_not_contained`）— 設定で外せない安全の床です。

**1 サーバーに生きているグラントは最大 1 つ**（v1）。

## 状態

グラントと目標はそれぞれ**実際の**状態を持ちます。ダッシュボードの見出しはそこから導かれ
（優先度の高い方）、書き戻されません。

| グラントの状態 | 理由 | 誰が戻すか |
|---|---|---|
| `active` | — | — |
| `paused` | `user`、`goal_paused`・`goal_blocked`・`goal_budget_limited`（目標が進行中でない） | ユーザー（操作トークン）。予算切れ: 新しいグラント。`blocked(max_iterations)`: 新しいグラント（v1） |
| `halted` | `breaker_warning`（WARNING / COHERENCE）、`breaker_critical`（CRITICAL・不明） | ユーザーが `RESUME` と入力 + 操作トークン。ブレーカーが NORMAL のときだけ。次の tick で再確認（`recheck`） |
| `revoked`（最終） | `user`・`kill_switch`・`restart`・`session_reset`・`clock_anomaly`・`unhealthy` | 新しいグラント |
| `expired`（最終） | `ttl` | 新しいグラント |
| `ended`（最終） | `complete`（ユーザーが確定） | — |

| 目標の状態 | 意味 |
|---|---|
| `active` | 作業を続けてよい（W5） |
| `paused(user)` / `blocked(<理由>)` / `budget_limited` | グラントは `paused(goal_<状態>)`。理由は `no_progress`・`loop_detected`・`max_iterations`・`same_blocker`・`approval_timeout`・`verification` |
| `awaiting_verification` | エージェントの完了主張（W5）でここへ。動けるのはユーザーの確認だけ。グラントは `active` のまま |
| `complete(verified)` | グラントが `active` の間にユーザーが確定した |
| `unmet(<グラントの終わり方>)` | 先にグラントが終わった |

規則（ADR 0011 §8, §11。各行を `tests/test_grants_state.py` で固定）:

* グラントの一時停止は、目標の `blocked` / `budget_limited` を上書きしない;
* グラントの終了状態は最終。終了後の確認は `late_verification`（`pass` / `fail`）として
  記録するだけで、何も生き返らせない;
* `complete` はグラントが `active` の間にユーザーが確定したときだけ。エージェントの主張は
  目標を `awaiting_verification` にするだけ。差し戻すと `active` に戻り、進展なしの 1 tick
  として数える;
* 再開は停止前の状態に戻る（ユーザーの一時停止を中断した停止は、その一時停止へ戻る）;
* 予算はグラントごとに積み上がり、決してリセットしない。TTL は延長しない;
* **自動停止**（ブレーカーのフック・キルスイッチのリスナー・`/new` はメモリ内で即時。それ以外は
  権限ウォッチドッグの 15 秒ごとの巡回と毎リクエスト、そして W5 の入口 `authority_record` と
  `claim_complete` が通る `check_now(grant_id)`）: キルスイッチ → `revoked(kill_switch)`、権限またはグラントストアの異常 →
  `revoked(unhealthy)`、ブレーカーが NORMAL を離れる → `halted(breaker_*)`、前回から壁時計
  が戻る、または壁時計とスリープ込み時計の食い違いが 5 秒を超える（前後への飛び） →
  `revoked(clock_anomaly)`、TTL（3 つの時計の差の最大。スリープも数える） →
  `expired(ttl)`、`/new` → `revoked(session_reset)`、毎回の起動 → `revoked(restart)`。
  **どの停止も権限エポックを進めます**（停止 ID = `(incarnation, epoch)`）。NORMAL への
  復帰・時間の経過・チャットのメッセージで停止が解けることはありません。

スリープ込みの時計が別に無いホストでは、スリープが飛びに見えてグラントが取り消されます
（安全側）。

## グラントストア `grants.json`

データディレクトリ内、`0600`、権限ファイルと同じ安全なオープン規則（シンボリックリンク・
ハードリンク・FIFO・他の所有者は不可。フラッシュ付きの原子的置換。置換の前と毎回の巡回で
読み直す）。最新 4 レコード、それぞれ状態全体を持ち、`seq` と前のレコードのハッシュで鎖に
なっています。**グラントが active として保存されることはありません**: 生きているグラントは
次の起動でそうなる形 — `revoked(restart)`、目標 `unmet` — で書かれ、`restart_from` に生きて
いた状態が入ります。起動時にそれぞれをライフサイクルの遷移 `→ revoked(restart)` として記録
し、書き戻します。保持は最大 16 件。古い終了済みから消えます — その目標の文は、保持している
4 レコードのうち古いものには残り、それらが入れ替わる（あと 4 回の書込み）まで消えません。書込みは
1 本の上限付き・同時 1 つの書込みスレッド（`grants-persist`、W2 のキル永続化と同じ型）で行い、
リクエストは最大 1 秒（発行は 5 秒）、停止の手順はその持ち時間だけ待ちます（固まったディスクで
走っている書込みは置いていき、手順は `pending` と答える）。確認の巡回は状態が変わったときだけ
書きます（時計の読みはメモリ内）。読み手が拒む内容は書きません。

安全でない・読めない・形式が違う・変わったファイル、または書込み失敗で、この段は
**異常（固定）**になります: 生きているグラントはすべて取り消し（`unhealthy`）、発行できず、
ファイルは上書きしません。修復: サーバーを止め、`grants.json` の写しを残してから退避し、
起動し直します。

## 人の操作面

ルート（`autonomy.stage_c` のときだけ。サーバーの Host / Origin / CSRF の確認の内側。モデル
から見えるツールはありません。[admin-api-permissions](admin-api-permissions.md) 参照）:

| ルート | 内容 |
|---|---|
| `GET /api/grants`、`GET /api/grants/<id>` | 構造化された状態だけ: ID・コード・カウンタ・残り TTL・残り予算、（W6c）`claim_evidence`（最後の申告のコードとカウンタ。確認待ちの間は `waiting_sec` / `stale` / `stale_after_sec` も。申告の前は `null`）。目標の文も作業パスも出さない |
| `GET /api/grants/<id>/goal?confirm=SHOW` + ヘッダ `X-Stira-Goal-View` | 目標の文。発行した本人だけ、**1 回だけ**: 発行の応答にあった一度きりの閲覧トークン（メモリ内。最初の表示で消費、再起動で無効、再送の応答には入らない）と、入力した `SHOW`。`Cache-Control: no-store` |
| `POST /api/grants/issue` | `confirm: "ISSUE"` の入力**と**ホスト確認の操作: 最初のリクエストは 428 `grant_confirmation_required`（操作と一度きりの確認トークン）。`POST /api/grants/operations/<op>/confirm {token, acknowledged: true, instance}`（同一オリジンのブラウザからだけ）で確認し（`STIRA_YOLO_HOST_CONFIRM=command` / `dialog` のときはホストで確認。グラントは YOLO デスクの操作と実際のチャネルを使い、ブラウザでの確認は `host_confirm_on_host` で拒否。ページは `GET /api/grants/operations/<op>` を問い合わせる）、同じリクエストを `X-Stira-Host-Operation: <op>` 付きでもう一度送ります。操作は incarnation・本文・サービスの世代に結び付き、一度きり。対象が変わっていれば拒否。**同じ op id と同じ本文は元の結果を返し**（`replayed: true, historical: true` 付き: 今ではなく当時のグラント）、違う本文は拒否。エージェントのツール呼び出しが走っている間は操作のどの段も拒否（ステージ C がオンならツール呼び出しの追跡は YOLO の有無に関係なく入る。無ければ拒否）。**柵:** 最初に権限エポックを取り、グラントを耐久的に書いて（`revoked(restart)` として）から W1 の `commit_at_epoch` で公開します。その間のブレーカーの離脱・`/new`・キルスイッチ・権限の異常で中止（`grant_issue_aborted_epoch`）。書込みの失敗や 5 秒以内に戻らない書込みでも拒否（`grant_store_unhealthy` / `grant_store_timeout`） |
| `POST /api/grants/<id>/revoke` | ワンクリック。いつでも使える — ストアや権限が異常でも、ディスクが固まっていても: 取り消しとエポックの前進はストアの I/O より前にメモリ内で済む（1 秒以内に書けなければ `persisted: false`） |
| `POST /api/grants/<id>/pause` | ワンクリック |
| `POST /api/grants/<id>/resume` | 一時停止: 操作トークン。停止（halted）: `confirm: "RESUME"` の入力 + トークン、ブレーカーが今 NORMAL でなければ拒否。操作はグラントの世代・状態・停止エポックに結び付くので、古い停止への再開は拒否（`stale_operation`） |
| `POST /api/grants/<id>/verify {"decision": "confirm" \| "reject"}` | 発行と同じくホスト確認の操作。目標が `awaiting_verification` でグラントが `active` のときだけ。確定の直前に時計・キル・健全性・ブレーカーを読み直し、柵（W1 `commit_at_epoch`）の中で確定します。時計はその柵の**中で**もう一度読むので、TTL の確認と確定の間に隙間は残りません（W4.5）: 確認の後に期限切れ・停止したグラントはその停止になり、確認は記録だけ（`complete` にも、目標の再開にもならない）。終了後は最初の 1 回だけ記録（`late_verification`） |
| `POST /api/grants/operations/<op>/cancel` | 開いている操作の取り消し |
| `POST /api/authority/kill`（W2） | キルスイッチはすべてのグラントを取り消す（メモリ内で、キルのエポックで。グラントのライフサイクルイベントとストアの書込は、キル自身の永続化の試みと取消の開始の後） |

グラントと目標の遷移はすべて W2 の `lifecycle_event`（主体 `grant` / `goal` とグラント ID、
コードだけ）。停止系の遷移は既存のキー（`stop|grant|*|<理由>`）の停止通知になり、ストアの
健全性は主体 `grants` / `store` です。

**ダッシュボード:** ステージ C がオンのとき、設定ページに「目標グラント」の節が出ます:
見出し・目標の状態・残り TTL・残り予算・反復・停止理由、グラントごとの取り消し / 一時停止 /
再開 / 確認、キルスイッチ、発行フォーム。発行者だけの確認表示以外で目標の文は描画しません。

## ステージ C のホスト確認の設定

発行・再開・確認は権限を広げる操作なので、ブラウザのリクエストだけでなく**ホストにいる人**が要ります
（ブラウザのチャネルでは証明がすべて要求したプロセスに渡るので、同じユーザーのプロセス — exec の子、
MCP サーバー、切り離されたジョブ — が操作できてしまう）。そこでステージ C は YOLO デスクのホスト
チャネルを使います: `STIRA_YOLO_ALLOW` と `STIRA_YOLO_HOST_CONFIRM=auto`（macOS では OS が認証する
デスクトップのダイアログ）・`dialog`・`command`（TTY で `stira approvals decide <short>`）を設定します。
このチャネルが無ければ、これらの操作は拒否されます（`host_channel_required`、変える設定を添える）。
起動時の行に、どの層が効くかが出ます（`host confirmation (dialog)` / `(command)`、弱いブラウザの層、
または拒否）。ブラウザでの確認は、ユーザーが `autonomy` の `"allow_browser_confirm": true` で明示的に
選んだときだけ受け付けます — 弱い層で、起動時に記録します。取り消し・一時停止・キルスイッチには確認は
不要です。ステージ C がオンのとき、`/new` は常に権限エポックを進めます（狭める操作: それ以前に出た
他の保持者の許可証も無効になる）。

## 運用手順

1. オンにする: `gateway-config.json` → `{"autonomy": {"stage_c": true}}`、ホスト確認を設定（上）、再起動。
2. 発行: 設定 → 目標グラント → フォームを埋め、`ISSUE` と入力し、発行を押して確認に
   チェック。グラントは `active` になります。それだけでは**何も動きません**。
   `"stage_c_exec": true` もあるときは、反復ごとに **1 反復だけ実行** を押します。カードには
   承認ページで答え、完了の主張は「確認」で確かめます。
3. 止める: 取り消し（最終）、一時停止、またはキルスイッチ。停止（halted）は `RESUME` で再開。
4. 再起動はすべてのグラントを取り消します（`revoked(restart)`）: 新しく発行してください。

## 既知の制限

どれも権限を広げず、閉じる側に倒れます。残る項目は #620 で追います。

* **キルの順序（W4.5、#620 W5-3）。** キルのリスナーはメモリ内で取り消すだけ。グラントの
  ライフサイクルイベントとストアの書込の依頼は、権限側のキルの永続化の試みと取消の開始の後で
  走ります: 止まった記録係が遅らせるのはそれらで、キルではありません。その間に落ちても失うのは
  それらのイベントだけ（生きているグラントはどのみち `revoked(restart)` として保存される）。
* **確認の判断の時点（W4.5、#620 W5-2）。** 柵の中の確定で読んだ時計の値です。その後（書込の
  間）に TTL が過ぎても `complete` は戻りません（完了したグラントは何も許さない）。
* **書込係の失敗（W4.5、#620 R1）。** ストアの書込係で予期しない例外が起きると、ステージは
  不健全（`grant_persist_failed`）になり、生きているグラントはすぐにすべて取り消されます
  （`revoked(unhealthy)`）。
* **再送（W4.5、#620 R2）。** 再送された操作の応答は `historical: true`: 操作を適用した時点の
  グラントを表します。今の状態は `GET /api/grants/<id>` で読みます。
* **実行部の残り（W5）。** 取り消しはツールの境界で効きます: 走り出した `run_checks` や
  `editor` の呼び出しは最後まで走り、その間の停止（絞り込み、TTL、人のターン、壁時計の上限）は
  `<tool>_completed_after_stop` として記録します。
* **モデル呼び出しの最中の停止（W6-F、#640）。** 停止は、走っているプロバイダーの要求を取り消し
  ません: 反復はそれを待ちます — 0.5 秒の猶予と、モデル呼び出しが応答を読んでいる間はさらに最大
  5 秒（`STOP_DRAIN_SEC`。終了処理と壁時計の上限では待たない）。応答は子が見る前にすべて読むので、
  終わった呼び出しは使用量を報告します: それを計上し（総額と 1 tick 分。ハートビートで始めた反復の
  費用の行には `tokens_in` / `tokens_out` が入る）、予約の残りは 1 回だけ戻し、残りのコードは
  `model_completed_after_stop`。答えそのものは捨てます — 人のターンの後も含めて子には見せません
  （文だけの答えも子の履歴やターンの処理に入らない）。作用は続きません: 以後の境界はすべて拒否します。待っても終わらない
  呼び出しは見切ります: プロバイダーの要求に止まるよう伝え、見捨て（下記）、予約は全額計上のままです。
  W6e のスモーク（1 回の実行、見積もり）では、これまでこのような停止 1 回に、約 2.7k しか使わなかった
  呼び出しで約 71〜74k トークン（予約）を計上していました。
* **見捨てたプロバイダー呼び出し（W5）。** Python はソケットで止まった読み込みを取り消せません。
  プロバイダー呼び出しは専用のスレッド（`grants-call-<short>`）で動き、停止すると反復のスレッドは
  すぐに（上の猶予と待ちの後）終わり、呼び出しは **見捨てられます**: 遅れて来た答えは捨てる
  （以後の境界はすべて拒否: ツールも状態の変化もなし）、予約は全額計上のまま、残りのコードは
  `abandoned_call`、数を数え（実行部の状態の `abandoned_calls`）、**生きている間は新しい反復を
  受け付けません**（`abandoned_call`）。終了処理の段は `abandoned` と答えます。寿命を区切るのは
  プロバイダーのクライアント自身の読み込み / 接続のタイムアウトだけです: 実行部はチャットの
  エージェントと共有のモデルのオブジェクトを使い、そのクライアントは変えません。
* **同じユーザーのファイルシステムの操作者（W5、対象外）。** サーバーと同じユーザーの別の
  プロセスは、editor の砂場の最後の確認と書込の間に、許可したディレクトリの名前を変えられます。
  書込はその名前を変えたディレクトリに入ります。根は受け入れ時と消費のたびに固定しますが、その
  最後の瞬間は越えません。W1・W2・W4 と同じ前提です（同じユーザーのプロセスは `grants.json` や
  設定を含め何でも編集できる）。エージェント自身のツールにはできません: 名前を変えるツールはなく、
  `run_checks` は使い捨ての写しで動き、その砂場は実行ディレクトリの外への書込を拒否します
  （xfail のテストで固定）。
* **デバッグログのフィルター（W5）。** プロバイダーの通信とツール実行の DEBUG 行を落とす
  フィルターは実行部と一緒に入り、プロセスの間ずっと残ります（軽い。INFO 以上は隠さない）。
* **`/step` と同じユーザーのプロセス（W5、設計どおり）。** `/step` は、人がホストで確認して
  発行したグラントを *使う* だけで、権限は作りません（発行・再開・確認はホスト操作のまま）。
  ダッシュボードの CSRF / Origin の境界は、同じユーザーのローカルのプロセス（CSRF トークンを取った
  クッキーなしの API クライアントも）と人を区別しません — チャットのカードの承認や設定の編集を含め、
  どのルートでも同じです。モデルにはダッシュボードの API への道がありません（自分のダッシュボードの
  ガード）。1 回の step が使うのはそのグラント自身の予算・TTL・範囲だけで、エージェントのツール
  呼び出しの間は拒否します。見捨てた呼び出しで走っている `run_checks` は自身のタイムアウト（300 秒
  以内、一時ディレクトリの中）で終わります。
* **プロンプトキャッシュ（W5）。** 反復のモデル呼び出しは **プロンプトキャッシュなし** で動きます
  （子にとって包んだモデルは独自のモデル。キャッシュ設定済みのモデルを直接渡した場合も、
  キャッシュされるのは静的な先頭だけで、文脈ブロックは常にその後ろ）。信頼済みブロックの費用は
  Stira の見積もりでモデル呼び出しごとに約 355 トークン（英文の見積もり誤差の実測から 355〜515。
  トークナイザーでの計測ではない）。目標でさらに最大約 500。
* **他のターン（W5。W6b で解消）。** ターンのロックを持つものは**すべて**割り込みます: ロックは
  1 つの `TurnLock`（`src/stiracore/core/turn_lock.py`）で、取る手段はそれだけです。取る側 — 人の
  チャットのメッセージ（進捗報告への返事・方向修正も）、webhook のターン、自動の続き、復元した
  カードの再開、`/new`、手順の承認 — はどれもロックを試す**前**に合図します（W5 では webhook・
  自動の続き・再開に合図がなく、そのターン中に作用が終わっても残りとして記録されず、終わりの
  記帳もずれていました）。合図はカウンターを進め、取る試みが終わるまで「到着中」の印を立てます。
  実行部は印を先に、次にロックを読むので、合図からロックを放すまで押下は通りません — 再開が
  ロックを待つ間も、合図とロックの間の一瞬も。走っている反復は次の境界で譲ります
  （`yielded(user_turn)`）: モデル呼び出しの前（要求を送る直前にもう一度）、ツール呼び出し、
  承認待ち、報告の前。待っているカードはすぐ引っ込めます。残り: 既に送ったプロバイダー呼び
  出しは中断されません（答えの後に譲り、その答えから先の作用はない）。既に走っているツール
  呼び出しも同じです（`<tool>_completed_after_stop` として記録）。ロックが取られていて断られる
  試み（`turn_running` で断られたチャットのメッセージ、`/new`、手順の承認）も合図します: 無害です。
  ロックが持たれている間、反復は境界を越えません。自律のスイッチが切れている間、ロックに合図は
  なく、ただのロックとそのまま置き換えられます（戻り値も例外の型も同じ。並べてテスト）。
* **数えるテストとその限界（W6b）。** テストは `src/stiracore` と `dashboard/` 全体を AST で読み、
  2 つの許可リストと照合します: ターンのロックの**使い方**はどれも既知の形でなければなりません
  （リストにある場所での `.acquire()`、`.release()`、`.locked()`、リストにある場所での `with`、
  `TurnLock(…)` / `TurnLock.of(…)` か別の名前への束縛、`turn_lock=` キーワード、真偽 / `is None`
  の判定）。束縛したメソッド、ヘルパーへ渡すこと、`vars()` / `getattr()`、他の属性、内側の
  ただのロックの名前を出すことはどれも失敗にします（形ごとの否定の対照で固定）。ターンの開始は
  呼び出し先の名前（`agent` / `_agent` / `runner` / `run_turn`、`stream_async` / `invoke_async`、
  `resume_approved_request`、それらを `target=` にしたスレッド）で拾い、1 つずつ分類します。
  検査は**構文上**のものです: 動的に届くロック（計算した属性名、`eval`）や、別の名前の
  呼び出しで始まるターンは見えません。それはレビューで捕まえるもので、このテストではありません。
  W6-H: `TurnLock(…)` を作る場所（どの名前で読み込んだクラスでも）は、リストにある 2 か所に
  1 つずつだけ（サーバーの合図付きのロック、観察用アプリのロック）— だから共有のロックの代わりに
  合図の無い `TurnLock(threading.Lock())` を置くモジュールは、そこで取らなくても報告されます。
  束縛しない `TurnLock.acquire(lock)` も取る場所として数えます（それでも合図する。テスト済み）。
  さらに実行時のテストが、組み立てたサーバーの配線（extensions、ブループリント、ビュー関数と
  そのクロージャ）をたどり、届くターンのロックがどれも共有の合図付きの 1 つであること（ターンの
  ロックの名前のただのロックが無いこと）を確かめます。**W6d の置き場:** ハートビート / スケジューラーの
  モジュールにあるターンや目標の反復の開始は、テストの `W6D_STARTS` に登録しなければなりません
  （持ち手は共有のロックを取る場所か、`iteration:` の押下）。登録していないものはテストが失敗します。
  W6d は自分の呼び出し元を 1 つ登録しました: スケジューラーの `GrantTicker._press`（実行部自身の
  `step` の `iteration:` 押下）。
* **独立した裏の仕事は割り込まない（W6b の決定）。** スケジューラーのエージェントの仕事
  （`GatedJobExecutor`、ADR 0024。承認された実行の再開も）、記憶の仕事、蒸留は、それぞれ**自分の**
  子エージェント（自分のセッションとエンジン、予算、承認の関門）で動き、ターンの
  ロックを取りません。反復に割り込むことも、反復に割り込まれることもありません。**決定（W6-H、
  W6d のため）:** 無人の反復に対しても独立のままです — そのファイル書込と反復の書込を直列にする
  ものはなく、ロックも足しません。無人の反復はグラントの作業フォルダの下に閉じ込められ（エディターと
  `run_checks` はその中だけ。書込のルート・秘密と設定の床など既存のパスの床は、どの書き手にも
  効く）、人はそのフォルダの中で排他を当てにしてはいけません（予定の仕事や別のプロセスが同時に
  書くことがある。各終わりの読み直しはそれを変化として見る）。
* **まだ残るもの:** UI がポーリングのたびにカードを作り直す
  （R3）。一般のエポック移動の後の無駄な確認と、呼び出しごとのログ行（R4）。壁時計と起動時計の
  ずれが累積 5 秒を超えると（例: NTP のステップ）取り消し（`clock_anomaly`）（R5）。古い
  スナップショットのより厳しい検証と、窓が回るまでそこに残る目標の文（S1、S2）。初期のブランチ
  の `grants.json` は読み込めない（S3、開発データ）。同じユーザーの OS プロセスは `autonomy` を
  編集できる（C1、上に記載）。

## 目標の反復の実行部（W5）

`src/stiracore/grants/executor.py`。gateway の `autonomy.stage_c_exec: true` のときだけ作られます
（`autonomy.stage_c` が前提。オフ: 実行部のオブジェクトもルートもスレッドもファイルもない）。

**起動。** `POST /api/grants/<id>/step`（パネルで 1 回押す。サーバーの Host / Origin / CSRF の
確認の後ろ。入力語もホスト操作も不要 — グラントは発行時にホストで確認済み。モデルから見える
ツールにはならない）が反復を **1 回**、サーバーが持つスレッド（`grants-iteration-<short>`）で
始め、すぐに応答します。`GET /api/grants[/<id>]` は `iteration` を示します: `running` /
`yielded` / `idle`、終わりのコード（`done`、`claimed`、`reported_blocked`、`yielded_user_turn`、
`permit_stale`、`budget_refused`、`token_count_unavailable`、`approval_timeout`、
`run_checks_unavailable`、`timeout`、`model_error`、`tool_refused`、`stopped`、`shutdown`、
`failed`、`workspace_changed`、`no_action`）、詳細コード、カウンター（モデル呼び出し・ツール呼び出し・書込・チェック・承認待ち・
報告）、待っているカード（`card: waiting`）、残りのコード — 自由文はありません。

**受け入れ。** 押した時点で、サービスの確認（`authority_record` / `executor_record`:
`check_now`）から得たグラントが `active` **かつ** 目標が `active`（`awaiting_verification`・
`paused`・`blocked`・`budget_limited` は何も通さない）、キルなし、権限とストアが健全、ブレー
カーが NORMAL、反復が上限未満、壁時計 **と** 単調時計の両方で TTL が残る、予算が残る、チャット
のターンが走っていない、見捨てたプロバイダー呼び出しが生きていない、部分木が発行時のままの
ディレクトリ、信頼済みの指示文が読める、他の反復が
走っていない（サーバーに 1 つ。v1 は生きたグラントが 1 つ）。停止からの再開が残した `recheck`
はここで満たします: 上の確認を今行い、それから消します。拒否: `409 grant_iteration_refused` と
`reason` コード。

**セッション。** 反復は `delegate` と同じ作り方の専用の子（`agent/grant_child.py`）で動きます:
セッション `grant:<id>`、新しい Neural State（報酬や感情の更新はメインセッションに届かない）、
サーバーのその時のルールを読む自前の `CheckpointHooks`、床、`IdentityGuard`、結合の検証、
`scope.workspace_subtree` に絞った書込ルート、メモリ内だけのチェックポイント、観測フックなし。
チャットのセッション、その履歴、プロンプトキャッシュの先頭は変わりません。

**ツール** = `scope.tools` ∩ {`file_read`、`editor`、`run_checks`、`memory_read`、
`memory_search`、`memory_list`、`current_time`} ∩ その時のルール（Never: 渡さない）— と、
ハーネスのツール `goal_report`。シェル・Web・delegate / サブエージェント・handoff・
allow-again・連携・スケジューラーのジョブ・MCP のツールは渡しません（子のツール一覧をテストが
列挙）。Ask に答えるのは **人のカードだけ**（サーバーの承認ブローカー経由。YOLO も許可の
再利用もなし）。カードはセッション `grant:<id>` を名乗り、チャットのターンに属さず、その場限り
（再起動で取り消し、`grant_stopped`）で、反復が止まると引っ込めます。答えのないカードは反復を
終わらせ目標を止めます: `blocked(approval_timeout)` — 再試行はしません。グラントのカードの耐久的な記録と履歴に残すのは、決まった項目から作る **コードだけ**（ツール、
パスが部分木の中か、パスと引数のダイジェストの先頭、その大きさ、グラント id）— モデルが選んだ
文字列（パス、`cwd`、内容）は入りません。**その場のカード**（承認ページとチャットの通常の承認待ち
表示）は、人が何を承認するか見る必要があるので、パスを含む引数を表示します。普通の承認カードと
同じ見え方です（ローカルのダッシュボード、Host / Origin / CSRF の後ろ。モデルはダッシュボードの
API に触れない）。メモリにだけあり、カードが引っ込められる（反復の停止）、判断される、サーバーが
再起動すると消えます。`editor` は部分木の中だけ
（解決後のパス、シンボリックリンクで外へ出ない）で、許可証の前と **消費の後にもう一度** 確かめ
ます。受け入れ時と `editor` / `run_checks` の消費のたびに、部分木そのものが本物のディレクトリで、
解決したパスが発行時に保存したものと同じでなければなりません（解決し直さない）: 違えばその作用を
拒否し、目標は `blocked(workspace_changed)`。`run_checks` は呼び出しのたびに範囲、`autonomy.run_checks_unattended`、その時点で確認済み
の `os_sandbox` が必要です（`run_checks` 自身も実行前に砂場を確かめる）。どれかが落ちていれば
その呼び出しを拒否し、目標を止めます: `blocked(run_checks_unavailable)`。

**作用ごとに許可証 1 枚。** モデル呼び出し・ツール呼び出し・承認待ち・`goal_report` のたびに、
W1 の許可証（インカーネーション、エポック、グラント id、世代、TTL の組。モデル呼び出しは予約 id
も）を取り、I/O の直前に消費します。消費の前にもう一度確認し（時計・TTL・キル・健全性・
ブレーカー・グラントと目標の状態）、反復自身の停止（人のチャットのターン、壁時計の上限、終了）
を読みます。許可と消費の間の停止 → `permit_stale`、作用なし。待ち（カード、遅いモデルの答え）
の後の作用は新しい許可証を取ります。許可証は発行時のエポックを越えません。消費した作用は W1 の
実行中の集合に入ります: 絞り込み（キル・取り消し・ブレーカー・`/new` など）は子を次の安全な点で
取り消し、待っているカードを引っ込めます。それでも終わった作用は記録されます
（`<tool>_completed_after_stop`）。

**予算。** プロバイダーへの要求の前に、**最終の**入力（送る通りのメッセージ・ツール定義・
システムプロンプト。文脈ブロックを含む — **モデル自身の整形器で整形**するので、`additional_args`
などの要求の上書きも含む）に **手元で控えめな上限** を付けます: JSON の形の UTF-8 の 1 バイト
= 1 トークン、要求・メッセージ・ツールごとの固定の上乗せ（バイト単位のトークナイザーの 1 トークン
は 1 バイト以上）。出力の上限は整形した要求が持つものです。**数えるためにプロバイダーへ要求は送りません**
（プロバイダーの `CountTokens` は確認の前に目標を送ってしまう）。`上限 + max_tokens` を
グラントの総額・1 tick の上限（1 tick = 1 反復）・共有プールに対して予約し、収まらない呼び出しは
送りません（`budget_refused`）。整形器がない、JSON にできない要求（生のバイト。例えば埋め込みの画像・
文書）、要求に出力の上限がない → 呼ばない（`token_count_unavailable`）。反復はチャットの
エージェントのモデルの **写し** を使います。Bedrock では写しのクライアントが、**すべての**最終の
要求（`converse_stream` / `converse`）の直前に停止・ターンのロック・グラントを確かめて許可証を
取るので、1 回のモデル呼び出しの中で SDK がやり直す要求（ツール結果のターンの回復）も停止の後は
何も送りません。botocore の中の同じ HTTP 要求の再送は別の要求ではありません。他のプロバイダーは
すべて拒否します（`provider_unsupported`）。呼び出しごとにクライアントを作る Strands のプロバイダー
（OpenAI、Ollama、LiteLLM、Gemini、Mistral など）も同じで、すべての最終の要求を守れるプロバイダー
だけが反復を動かします。報告された使用量（入力 + 出力 + キャッシュ。差額は戻す。不明なら
予約全額）で `state.charge` に計上し、予約は必ず 1 回だけ終わります。停止の後に終わった呼び出しも
同じです（W6-F、#640、[既知の制限](#既知の制限)）。予約全額のままなのは、見切った呼び出しと使用量が不明な呼び出しだけです。上限は同じ要求の Stira の
見積もりの約 4 倍です（実測: editor・`file_read`・`current_time`・`run_checks`・`goal_report`
の最初の呼び出しで 6,466 対 1,618）: 発行フォームの既定（運用者の決定 2026-10-25: 総額 2,000,000、
1 tick 200,000。上限 5,000,000 と 1 tick ≤ 総額は変わらない）と `max_tokens` 8,192 では、反復は
約 25 回のモデル呼び出しで `budget_refused` になります（1 往復あたり約 1 KB の新しい文で実測。
ツールの結果が大きいほど少ない。1 tick 20,000 では約 2 回）。上限は緩めません。1 tick の上限はこれに合わせて選んでください。総額は戻りません。反復は 1 回ずつ数えます（`state.count_iteration`）。進展したかは
活動ではなく**結果**で決めます（W6a、[下](#結果による進展w6a)）。

**文脈。** モデル呼び出しごとの入力は、最新のユーザーメッセージの写しに付けた 1 つのブロックで
終わります: 信頼済みの指示文（`src/stiracore/grants/dev_playbook.md`。人だけが編集し、読み取り
専用で読む。その SHA-256 が反復の開始イベントのコード `playbook_<12 hex>`）と、末尾に目標
（#254）。目標は子の履歴・メインセッション・チェックポイント・ライフサイクルイベント・outbox・
表示・エラー・ログ行のどこにも入りません（実行部がある間、プロバイダーの DEBUG の要求ダンプは
捨てる）。

**報告。** `goal_report(kind, code)`、固定の列挙だけ: `progress`（`step_done`、`tests_written`、
`checks_run`、`investigating`。メモリ内だけ）、`blocked`（`needs_decision`、`out_of_scope`、
`missing_input` → 目標 `blocked(<code>)`）、`claim_complete`（`goal_met` → 目標
`awaiting_verification`。`complete` には**決して**ならない）。後の 2 つは反復を終えます。
ツールの呼び出しも報告もない返答は `no_action` として反復を終えます。

**割り込みと上限。** ターンのロックを持つものすべて（W6b: 1 つの `TurnLock`。人のチャットの
メッセージ、webhook のターン、自動の続き、復元したカードの再開、`/new`、手順の承認）が、ロックを
試す前に合図します。反復は次の境界で譲ります（`yielded(user_turn)`: 走っている作用は中断しない。待っているカードは引っ込める）。
`/new` は取り消し（`revoked(session_reset)`）で、それにより止まります。
`autonomy.iteration_wall_sec`（既定 600）で `blocked(iteration_timeout)` として終わります（境界
ごとと、ウォッチドッグの巡回で確認）。終了処理の段（`grant_executor`、承認が閉じる前）は予算内で
止めて合流します（`pending`: プロバイダー呼び出しの中に残ったスレッド）。

ライフサイクルイベント: 対象 `grant_iteration`（グラント id）: `idle → running` に指示文の
コード、`running → idle | yielded` に `iteration_<end>`。

## 結果による進展（W6a）

W5 は、ファイルを書いたかチェックを走らせた反復を進展と数えていました。これは活動を数えています。
同じバイトを書き直す反復や、同じ失敗のチェックを走らせ直す反復はいつまでも進展に見え、
`blocked(no_progress)` が決して出ませんでした。W6a は**結果**から決めます。決定的で、モデルは
呼ばず、何も広げず、完了の主張は今もユーザーが確認します。**モデルによるループの判定はありません。**

**指紋。** 反復が終わると、実行部は鍵付きの指紋を 1 つ作ります（`src/stiracore/grants/progress.py`）:
グラントごとの乱数の鍵（メモリ内だけ。グラントは再起動を越えず、鍵も越えない）による HMAC-SHA256 で、
次の正準な符号化にかけます。

* **作業フォルダの識別**: 反復の終わりに、グラントが書いたすべてのファイルを**その場で読み直したもの** —
  相対パスの HMAC と、いまのバイトの HMAC。なくなったファイル（誰かが消した・名前を変えた）は明示の
  「なし」の印になります。ファイルを追うのは、ある反復がそれを変えたとき（その反復で最初に書く前のバイトと
  終わりのバイトが違う）、または変化を観測できずに書いたとき（中断された、unknown）です — そのファイルは
  その書込の**前の**バイトを直前の分かった状態として入るので、バイトが変わったときだけ識別を動かします（W6-H:
  中断で失われた新しいファイルの同じバイトの書き直しは何でもなく、本当の変化は次の終わりに見える）。書く前の
  バイトを読めなかったファイルは、その終わりからは追いません。同じバイトに
  戻った書き直しは何も足しません。パスは**最近書いた 256 個まで**。古いものは識別から黙って外れます（数は
  残さない）。stat のキャッシュ（デバイス・inode・サイズ・mtime・ctime）は変わっていないファイルを読み直さない
  ためだけのもので、変わったファイルは必ず読み直します。unknown の終わりも確かめたキャッシュの項目は残すので
  （W6-H）、予算に収まる追跡中のファイルは、落ち着いた読み取り 1 回で元に戻ります。こうして、反復の間に人が書いたファイルを編集・改名・
  削除しても変化になり、誤ったループにはなりません;
* 反復のチェックの結果を**チェックごとの行の 1 つの集合**として — その反復のすべての `run_checks` 呼び出しの
  和集合（重複なし、並べ替える: 同じチェックをもう一度・何度も・別の順に・別の呼び出しの分け方で走らせても
  同じ結果）。こうしてチェックの結果は、それが走ったファイルに結び付きます。

エージェントの `goal_report` は指紋に**入りません**（ラベルは結果ではない）。同じ障害の規則だけに使います。

| ツール | 指紋に入るもの | 取り除くもの（決して入らない） |
|---|---|---|
| `editor` | 書いたファイルのいまのバイトと、その相対パス（識別の一部として。64 MiB を超えるものはサイズと 3 MiB の見本） | mtime、inode、モード、使ったコマンド、何も変えなかった書込のバイト（どの大きさでも） |
| `run_checks` | チェックごと（1 呼び出しに 16 個まで、1 反復に異なる行 64 個まで）: 種類、状態、理由のコード、終了コードの分類（`zero` / `one` / `other` / `none`）、passed / failed / errors / skipped / findings の数（1,000,000 で頭打ち）。チェックのない結果は 1 行（状態・理由） | 所要時間、pid、一時パス、時刻、id、失敗の id と文、出力、ツリーの変更、制限値、フォルダー、隔離の種類、呼び出し全体の状態、実行の順番・回数・分け方 |
| 読むツール | 何も入らない | — |

`[a-z][a-z0-9_]*`（40 文字まで）に合わないコードは `other` として入ります。

**ファイルのバイトの読み取り**は FIFO で待たず、シンボリックリンクもたどりません: リンクをたどらない非ブロッキングで
開き、読む前に `fstat` します。読むのは通常のファイルだけ（FIFO・デバイス・フォルダーは読めない扱い）。
`O_NONBLOCK` はストレージの遅延を抑え**ません**。抑えるのは反復ごとの予算です: 1 反復でダイジェストするのは合計
**256 MiB** まで（書く前と終わりの読み取りの合計。超えると unknown）、識別から外れるところのファイルは読みません。
**64 MiB** を超えるファイル（ほかの誰かが大きくした、など）は、サイズと、バイトの限られた見本（先頭・中央・
末尾の 1 MiB ずつ。予算から 3 MiB を引く。中身のダイジェストと等しくならないよう印を付ける）のダイジェストで識別し、
mtime や inode は**決して**使いません: `touch`、同じバイトを新しい inode にコピーするバックアップなど、メタデータだけの
変化は進展になりません。サイズの変化や見本の範囲の変化は進展です。既知の制限: そのようなファイルの、サイズが同じで
見本の外だけの変更は見えません（エディターはそれほど大きなファイルを書かない）。ダイジェストをキャッシュするのは mtime が 2 秒以上前の
ファイルだけです（1 秒単位の時刻）。途中で変わった読み取りは捨てます: 開いたファイルのデバイス・inode・サイズ・
mtime・ctime が読む前後で一致し、読んだ後のパス自体の `lstat` とも一致しなければなりません。普通の同時の書込や、
パスでのファイルの差し替えはこれで分かります。ファイルを書き換えて時刻を戻す同じユーザーのプロセスには**守りに
なりません**（W5 の既知の制限の、同じユーザーによるファイルシステムの競合）。

**分類。** `none`: 何も観測されない — チェックがなく、読み直した作業フォルダの識別が直前の分かった結果と同じ
（読んだだけ、報告しただけ、同じバイトに戻った書き直し — どれも作業フォルダが変わっていないとき）: 進展なし、
履歴に 1 枠。追っているファイルを**誰が**変えても（エージェントでも人でも）観測します。反復自身の編集が
何も変えなくてもです。`unknown`: 必要なものが何か読めない（ファイルの
ダイジェスト、途中で変わった読み取り、FIFO、権限のエラー、チェックの結果、1 反復で 256 個を超えるファイルの
書込や 64 個を超える異なるチェックの行）: **進展なし（閉じる側に倒す）、履歴に入れず、ほかの連続も変えない**。
次の終わりにはすべてを読み直すので、同じ読めないファイルはまた unknown です。`repeat`: 指紋が、直近 16 個の
分かった結果の中にある。`new`: それ以外。**進展は `new` だけ。**

**規則**（`progress.py` の名前付き定数。既定は ADR 0011 §8 のとおり）:

| 規則 | 目標を止める |
|---|---|
| 数えた反復が `no_progress_ticks`（既定 3）回続けて `new` でない | `blocked(no_progress)` |
| 直近 **6** 個の分かった結果のどれかの `repeat`（A-A、A-B-A-B、A-B-C-A。`none` の反復は 1 枠を取り、`unknown` は取らない） | `blocked(loop_detected)` |
| 同じ `goal_report(blocked, code)` が数えた反復で **3** 回続く | `blocked(<code>)` の代わりに `blocked(same_blocker)` |
| `no_action` の反復が（最後の再開から）**2** 回続く | `blocked(no_progress)` |
| `max_iterations`（変更なし） | `blocked(max_iterations)` |

**A-A をループとする理由。** 数えた反復が 2 回続けて同じ作業フォルダの識別・同じチェックなら、2 回目は何も
していません（同じファイルに対して、いま走らせたものをまた走らせた）。3 回を待てば、何もしないモデルの反復を
もう 1 回使います。代償: 最初の同じ再実行で止まります — 状況をつかむために読み直してチェックを走らせ直す
だけの反復もです。人が再開しても履歴は残るので、**ループの後、エージェントはまず何かを変える必要があります** —
同じファイルに同じチェックを走らせ直すと、すぐにまた止まります。人が戻した変更をもう一度当てると、前に見た
状態になります: 同じチェックならそれもループです（その時点から正味の変化がない）。

障害の報告は今も目標を止めます（`blocked(<code>)`。反復の終わりに、結果を確定してから）。人が再開し、
**分かって確定した**結果で同じ障害が 3 回続けば専用のコードでそう示します（unknown や中断の障害の報告は普通の
コードで止め、この数には入れない） — この連続は再開をまたいで残り（そうでないと 3 に届かない）、数えた反復が別の終わり方を
すれば数え直します。これはラベルであって錠ではありません: 人が答えた後に同じコードで新しい質問をしても
`same_blocker` で、再開できます。再開は進展なしの連続を数え直します（W5 のとおり）が、履歴は残すので、
再開をまたぐループも見つかります。完了の主張はこれらの規則で止まりません: 人の確認に回ります。モデル呼び出しを
使った後のプロバイダーのエラー（`model_error`）は、進展なしの数えた反復です（W5 から変更なし）。

**中断された反復** — 人のチャットのターン（`yielded_user_turn`、または最後の作用の後に届いたターン）、
`shutdown`、緊急停止、取り消し / 権限の縮小（`stopped`）、`permit_stale`、置き去りにしたプロバイダー呼び出し、
またはグラントが反復自身の終わり方の残した状態にない（取り消された・一時停止された・halt された・ほかの誰かが
止めた、または反復の開始の後にグラントが止まったことがある）— は連続も履歴も変えません。中断はグラント自身の
状態も含めて、ダイジェストを読んだ後の**確定のとき**にもう一度読むので、その読み取りの間の停止・取り消し・
一時停止も中断になります。反復自身の終わり方は中断ではありません: 完了の主張はそのものとして確かめ、自分の停止（障害の報告、自分の時間切れ）は
この確認の**後**で当てます — だから読み取りの間の人の停止（同じ理由での停止でも）を自分のものと取り違えません。
確認と数えることは**1 つの段**です（W6-H）: 確認でグラントの版（`generation`。グラントが変わるたびに進む）を読み、
サービスは自分の停止を当てて反復を数える同じロックの段（`commit_iteration`）の中でそれを比べます — 確認の後に
届いた人の停止・一時停止・止める操作は、そこで反復を中断にします（履歴にも連続にも入らない）。検出器の停止
（ループ、何もしない）も、その数えた版にだけ当てます。`max_iterations` には数えます（作用を使ったので）。グラントの間にチャットを 5 回送っても目標は
`active` のままです。数え方は反復を止めたものによりません（W6-F、#643）: 取り消し・`/new`・TTL・
緊急停止も一時停止と同じく数えます — 停止で終わったグラントでは `iterations` だけが動きます（連続も
状態も変わらない）。作用を 1 つも使わなかった反復は、何が止めても数えません（下記）。

**作用を 1 つも使わなかった反復**（モデル呼び出し・ツール呼び出し・待ち・報告がない — 準備の失敗、最初の呼び出し
の前の予算やトークン数による拒否、最初の消費での古い許可）は、終わり方によらず**まったく数えません**: 反復も
連続も履歴も変わりません。そのコード（`failed`、`budget_refused` など）で終わり、人がもう一度押します。

**ループの規則の代償。** 「戻してやり直す」がループとして止まるのは、グラントが書いたすべてのファイルの**いまの**
中身（この反復が触ったものだけでなく、読み直したもの）**と**反復のチェックの集合が、直近 6 個の分かった結果の
どれかと同じときだけです。それは実際に正味の変化がないので、人が再開します。ファイルを変えてから同じ失敗数の
チェックを走らせるのは `new`（識別が違う）。グラントが書いた別のファイルが変わった後で 1 つのファイルを戻すのも
`new`、反復の間に人が書いたファイルを編集したのも `new` です。**256 個を超えるファイル**にまたがる循環は見つかる
とは限りません（古いパスは識別から外れる）。`max_iterations` とトークンの上限は変わらずグラントを抑えます。
変化の検出は改善の判断ではありません: 関係のない編集も `new` です。それはトークン・TTL・`max_iterations` の上限と、
人の確認が抑えます。

**残すもの。** メモリ内だけ: グラントごとに HMAC 16 個の輪（各 32 バイト、または `None`）、書いたパス（256 個まで、
stat のキャッシュと直前の識別のもとになったダイジェストとともに — 実際のパスだがメモリ内だけで、表示もログもしない）と小さな連続の数 2 つ、最大 16 グラント分
（最も長く使われていないものから外れる。終わっていないグラントは外さない）。パス・ファイルの中身・目標の文・コマンド・
出力・引数は、どの保存先・ライフサイクルイベント・outbox・表示・`/api/activity` の grant ブロック・承認のデータベース・
例外・ログ行にも入りません（目印のテストがすべてを読む）。Stage のボードと表示に新しいものは出ません（終わり方
`no_action` の言葉だけ）。

## 完了の申告: 証跡と確認待ち（W6c）

v1 では完了を確かめるのは**人**です。エージェントは申告するだけで
（`goal_report(claim_complete, goal_met)` → 目標 `awaiting_verification`）、`run_checks` は証跡に
すぎません。W6c は、その時点で人が見る情報を増やします。**決める人は変えず**、モデルに文を保存先へ
書かせることも**しません**。コードだけで、ハーネスが観測した結果から測ります（モデルの言葉ではなく
実行時の結果から。OpenClaw `announce.md`）。これに基づいて何かが動くことはありません（自動の差し戻し・
確定もモデル呼び出しも無し）。

**記録**（グラントの `claim_evidence`。グラントの他の項目と一緒に `grants.json` に入る。グラントごとに
**1 つ**で、次の申告で置き換わる（追記しない）。差し戻しの後もその時まで残り、確定の後は監査の記録
として残って閲覧だけで表示される）:

| 項目 | いつ | 意味 |
|---|---|---|
| `claimed_at` | 申告時 | 申告の壁時計の秒（申告そのものがサービスのロックの下で読む時計。読めなければ申告は拒否） |
| `iteration`、`max_iterations` | 申告時 | 申告した反復 k（反復の終わりで数える）と最大 |
| `used_tokens`、`budget_left` | 申告時 | グラントのそれまでのトークン / 総量の残り |
| `ttl_left_sec` | 申告時 | その時点の残り TTL |
| `checks` | 反復の終わり | **失敗側に倒す** — `pass` は積極的に確かめられたときだけ。グラントのエディタの最後の書き込みの後の**すべての** `run_checks` 呼び出し（作業ツリーが同じ間は反復をまたいで合わせる）の判定: どれかが `fail` → `fail`（不合格・エラー・上限で停止の行。後から狭い合格の呼び出しがあっても隠れない）、それ以外でどれかが `unknown` → `unknown`、すべて合格のときだけ `pass`。呼び出しが `unknown` になるのは、結果が読めないか自己矛盾しているとき: ランナーが例外・チェック行が無い・未知の状態・16 行超・`consistent: false` の行（終了コードと報告が食い違う）・数が欠けている／数でない／失敗を報告している合格の行・全体の状態が最悪の行と違う・`real_tree_changed`。エディタの書き込みと重なった呼び出しは数えない。作業ツリーの同一性が読めていないことで、記録済みの `fail`（や `unknown`）が忘れられることは無い: 前の判定を置き換えるのは両方の同一性が読めていて違う（はっきり別の作業ツリーの）ときだけで、それ以外は合わせる。そのうえで `pass` / `fail` を出すのは、申告の作業ツリーの同一性（申告した反復の終わりが読む）がチェックの走った同一性（その反復の終わりに読んだもの）と同じときだけ: 違えば `not_run`（チェックの後でファイルが変わった。グラント・人・誰によるものでも、反復の間も含む）、どちらかが読めていなければ（例: チェックの反復が中断した）`unknown`。一度も実行していないか `run_checks` が拒否したときも `not_run` |
| `check_rows` | 反復の終わり | チェックごと（≤ 16、`pass` / `fail` のときだけ）: 種類（`pytest`・`unittest`・`node_test`・`ruff`・`compileall`、ほかは `other`）、状態（`passed` / `failed` / `error` / `limited`）、合格・不合格・エラー・スキップ・指摘の数（1,000,000 で頭打ち）。テスト ID・メッセージ・出力・パス・所要時間は入らない |
| `workspace` | 反復の終わり | 前回の申告から（最初の申告は発行から）`changed` / `unchanged`。W6a の作業ツリーの同一性（グラントが書いた全ファイルの読み直し）から。今回か前回の申告の同一性が読めなかったとき（中断・unknown の結果）は `unknown`。ダイジェスト・パス・HMAC・ファイル名は保存しない |
| `progress` | 反復の終わり | 申告した反復の W6a の結果の分類: `new`、`repeat`、`none`（観測なし）、`unknown`（中断。例: 申告の直後に人のターン。または読めない） |

申告と記録の前半はグラントサービスの 1 つの手順です（申告は 1 つのライフサイクルイベント
`goal: active → awaiting_verification`、`goal_claimed`）。測った後半は申告した反復の終わりに、その
ボード書き込みの中で埋まります。これは**状態変化ではありません**: 世代もイベントも通知も無く、記録が
もう一度書かれるだけです。埋めるのは**その申告の**記録だけ（`claimed_at` で特定）で、申告した反復の数え方が
**確定した**ときだけで、しかも**出すその時点で**（記録を**置く** 1 つの手順の中、サービスのリーフロックと権限の W1 の柵
`commit_at_epoch` の内側で）グラントがその確定の残した版（`generation`）のまま、反復の**開始時**に読んだ権限のエポックが動いて
いない（その後の狭める操作。申告の後、終わりの読み取りの間のものも含む。キル）、反復の開始から人のターンが合図していない・
来かけていない（ロックなしで立つターンの印とキルの旗は、置く直前に最後に読む）、申告が生きているグラントの上で
待っている、のすべてが成り立つときだけです。その間に取り消し・一時停止・キル・狭める操作・人のターン・人の
確認が入れば**何も**出しません（測ったコードは `unknown` のまま。測る前に確定されたら、監査は人が見たとおりのまま）。状態は
一切変えません。チェックの判定・それを結びつける同一性・申告時の作業ツリーの同一性は W6a の追跡器と並べてメモリにだけ持ちます
（グラントは再起動を越えません）。

**敵対的なモデル。** モデルが入れられるのは固定の列挙の `goal_report(kind, code)` だけです。どの項目
にマーカーを入れても、余分な項目やオブジェクト以外の入力も拒否され（`report_invalid`）、何も記録され
ません。同じターンの 2 回目の申告や blocked の報告の後の申告は、その境界で拒否されます（最初の終わり
方が勝つ）: 申告 1 回・イベント 1 つ。人のターンの最中の申告は適用前に譲ります。申告の直後に人の
ターンが来たときは申告はそのまま残り、測ったコードはすべて `unknown` です（確定していないので何も出さない）。他に何もしない即時の
申告は `checks: not_run`・`workspace: unchanged`・`progress: none` です。

**イベント 1 つ・通知 1 つ。** 申告は 1 つのライフサイクルイベントで、`awaiting_verification` は
停止系の状態なので、既存のキー（`stop|goal|*|goal_claimed`）の停止通知 1 件になり、人が既読にする
まで未読のままです。測ったコードの書き込みや look では何も増えません。差し戻しの後の新しい申告は新しい
イベントで、同じ通知に加わります（件数 + 1、最新のイベント、再び未読）。既存の停止通知の規則のままで、
新しいまとめ方は作りません。人がその申告を確認すると（確定・差し戻し・終了後の記録だけの確認）、その申告の通知を既読に
します。申告自身のイベント ID で行い、それは確認の自分のロック手順の中で、確認している記録の申告（`claimed_at`）のもの
であるときだけ読みます（「最新のもの」は使いません）。送信箱はそれが通知の最新のときだけ受け付けるので、新しい申告の分を
（確認の後に出たものでも）既読にすることはありません。

**確認待ちの状態。** 目標が待っている間（`awaiting_verification`、グラントが生きている）、ビューに
`waiting_sec`（`claimed_at` から、そのビューの時計で）、`stale_after_sec`（ゲートウェイ
`autonomy.claim_stale_sec`、60〜86,400 秒、既定 1,800。それ以外は既定値と警告
`claim_stale_sec_invalid`）、`stale`（`waiting_sec ≥ stale_after_sec`）が加わります。設定の欄は
「<時刻> から（n 分）」、証跡の行、閾値を過ぎると「まだあなたを待っています」を出します。
`checks: fail` の申告には「⚠」の注記を**言葉で**付けます（色だけにしない）。Stage のボードも同じです
（下）。表示だけで、閾値はタイマーを作らず、モデルを呼ばず、何も実行しません。

**確認は変わらない。** 確認のルート（ホスト確認、`confirm` / `reject`）の権限は変えません。差し戻しは
これまで通り進展なしの 1 回として数え（W4/W6a の規則）、グラントの終了後の確認は記録だけ、記録が
終わったグラントを生き返らせることは無く、終わったグラントへの新しい申告は拒否されます。

**保存形式。** `grants.json` の各項目は `claim_evidence`（`null` か記録。厳密に検査: キーの一致、既知の
コード、16 行以下、`pass` は全行が合格のときだけ）を持ちます。W6c より前に書かれた項目にはこのキーが
無く、`null` として読みます（アップグレード前の保存先も正常のまま）。それ以外のキーの欠けや未知の
キーは今まで通り拒否します。

**制限。** 同一性は W6a のもので、グラントが書いたファイルだけを対象にします。ほかのファイルの編集は
見えません。1 つの反復の中で、チェックの後その反復の終わりより前に他者が編集した場合は、終わりで読んだ
ものをチェックの走ったファイルとして扱います（同一性は終わりごとに 1 回読むだけで、余分な読み取りは
しません）。エディタの書き込みの後の `not_run` は保守的で、同じバイトを書いただけでも `not_run` です。
行の数は、チェックされたプログラムの報告が出す数です（上限つきの整数で、文ではありません）。公開は記録を
置いた時点で確定します: その後に来た停止（狭める操作・人のターン・キル・取り消し）は後の出来事で、記録は置いたときに
チェックの走った作業ツリーについて正しかった `pass` / `fail` のままです（停止そのものはグラントの状態が示します）。
ロックなしのターンの印とキルの旗は置く直前に読みます。その読み取りと辞書への格納の間の最後の一瞬に立ったものは、後の
ものとして扱います（W1 の柵つきの確定と同じ、受け入れた一瞬です）。

## ハートビート開始（W6d）

**既定でオフ、それも二重に。** ゲートウェイのスイッチ `autonomy.heartbeat_start`（既定 `false`。
`stage_c_exec` が必要。起こすのはチャットサーバーのスケジューラー — `STIRA_SCHEDULER=1`）**と**、グラント自身のフラグ `heartbeat_start`（既定 `false`）。
フラグは発行時に選びます: 発行フォームのスイッチ（「ハートビートで反復を始めてよい」。ゲートウェイの
スイッチがオンのときだけ表示）は発行の本文の一部なので、ホストで確認する操作のダイジェストに結び付き、
その要約にも出ます（`source: heartbeat_start`。ホストのダイアログ / コマンドにも）。あとから変える
ことはできません — 変えるルートはありません。取り消して新しく発行してください。どちらかがオフなら
スケジューラーの仕事もスレッドもなく、応答（`/api/grants`、`/api/activity`、グラントストア）も
これまでどおりです: `heartbeat_start` のキーと `tick` のブロックは、フラグ付きで発行したグラントにだけ
現れます。

**何が動くか。** スケジューラーの起動種別 `grant_tick`
（`stiracore.scheduler.grant_tick.GrantTicker`）。スケジューラー自身のループの毎回の tick で
ジョブのあとに評価されます（定期的な起床、最長 `max_wait_sec` = 30 秒ごと）。さらにハートビートの
tick のたびに *イベントによる* 起床があります（サーバーの tick 後のフックは起床の印を付けるだけで、
仕事はスケジューラーのスレッドがします — ハートビート自身はこれを import も実行もしません）。
**tick の経路にモデル呼び出しはありません**: 受け入れはグラントサービスのメモリ（`tick_record`:
最新の有効なグラント。確認処理なし、I/O なし）、ブレーカー、時計、ハートビートの健全性（スケジューラー
の ADR 0021 §8 の判定を毎回読む）、実行部のメモリ（`tick_facts`）を読むだけで、モデルもクライアントも
作らず、実行部の親エージェントも読みません。受け入れられたら、人の押下と **同じ**
`GoalIterationExecutor.step` を押します — 許可、予算の予約、ツールの許可リスト、先取り、確定の規則も
同じ。自分の条件も渡し、`step` はそれを自分の受け入れの確認で（プロバイダーを読む前に）、起床時の
グラントの停止エポックと一緒にもう一度確かめます: その間の停止や再開は拒否になります。
**1 回の起床につき最大 1 反復。**

**受け入れ条件**（すべて必要。最初に満たさない条件が見送りの理由）: スイッチ、実行部（停止中でない）、
キルなし、権限とグラントストアが健全、フラグ付きの有効なグラント、グラントが `active`、目標が
`active` — **`awaiting_verification` ではない**: 確認するのはユーザーだけで、申告が待っている間は
何も動きません —、ブレーカーが NORMAL、ハートビートが健全、読める時計で両方の時計に TTL が残っている、
反復が上限未満、予算が残っている、反復が実行中でも開始中でもない、放棄したプロバイダー呼び出しがない、
人のターンが来ていない・ターンのロックを持っていない（W6b: どの持ち手も先に合図を出す）、前の反復の
終わり（だれが始めたものでも）とグラントの発行（グラントの時計で。発行したばかりの人はまだ編集中かも
しれない）とグラントの最後の再開（W6-F、#644。グラントの時計で、発行と同じ測り方。再開時に時計が
読めなければ見送り）から **最低間隔** `autonomy.tick_min_spacing_sec`（既定 300 秒、下限 30 秒）が
過ぎている（つまり最後の終わりと最後の再開の遅い方から数える。終わりの時刻が読めなければ見送り）、**何もしない反復のゲート**（最後の人の押下
— その反復自身の終わりは数える — または再開 — 再開は停止のあとにしか来ず、停止のたびにグラントの
停止エポックが動く — 以降、`iteration_no_action` で終わった反復が 2 回続いたら、人が押すか再開する
まで見送り続ける。時間が経つだけでは解けない）、そしてイベントによる起床でだけ **洪水よけ**（60 秒に
ハートビートでの開始は最大 5 回。定期の経路には無い）。

**見送りは記録され、後回しにはされません。** `tick_skipped(<理由>)` — `not_enabled`、`no_grant`、
`grant_state`、`goal_state`、`awaiting_verification`、`heartbeat_unhealthy`、`breaker`、`kill`、
`authority_unhealthy`、`store_unhealthy`、`clock`、`ttl`、`max_iterations`、`budget`、`turn_busy`、
`iteration_running`、`abandoned_call`、`min_spacing`、`no_action`、`flood`、`executor_unavailable`、
`executor_refused`（実行部が断ったその他）— をグラントごとに数えます（メモリだけ、最近の 4 グラント）。
待ち行列もたまった分も再実行もありません: スリープや再起動のあとの起床は 1 回の起床です（逃した分は
まとめられる。ADR 0021 はモデルを呼ぶ仕事の追い付き実行を禁じています）。*状態による* 見送り（状態が
変わるまで続くもの: 上の理由のうち、混雑・一時的な `not_enabled`、`no_grant`、`turn_busy`、
`iteration_running`、`abandoned_call`、`min_spacing`、`flood`、`executor_refused` 以外）は、
ライフサイクルイベント `grant_tick` `active → paused` `tick_skipped_<理由>` を **1 回** 出します。
同じ理由をもう一度出すのは、その間にハートビートでの開始か別の状態による理由があったときだけ（間の
混雑による見送りでは足りない）、このプロセスでグラントごとに最大 32 件。ハートビートでの開始は `grant_tick`
`idle → running` `tick_started` を出します（グラントの `max_iterations` で上限あり）。tick の記録は
何も保存しません（ファイルなし）: 起動のたびにすべてのグラントは `revoked(restart)` なので、最初の
tick は何もしません（`no_grant`）。

**無人の反復**（`origin: tick`）は承認を待ちません: 規則がカードにする呼び出しが来たら、反復はすぐに
`approval_timeout` で終わります — カードなし、自己承認なし、YOLO の結び付けなし（W7）— そして目標は
`blocked(approval_timeout)`（人が再開します）。下限は変わりません: `run_checks` にはこれまでどおり
確認済みの `os_sandbox` ホストと `run_checks_unattended` が必要。範囲・ツール・予算はグラントのもの。
完了の申告を確認するのはユーザー。人のターン（ターンのロックのどの持ち手も）は、押下のときと同じく
これを譲らせます。

**コストの見える化。** ハートビートで始めた反復ごとに、数値だけ: モデル呼び出し回数、報告された
入力 / 出力トークン、プロバイダーが報告したときは `cache_read` / `cache_write`、経過時間
（`wall_ms`）。グラントのビュー（`/api/grants` の `tick.costs`、最近の 5 件）と反復のビュー
（`origin: tick`、`tokens_in`、`tokens_out` …。押下のビューは変わらない）に載り、Stage のボードは
最後の 1 件を表示します。W6e のスモーク（実モデルで人が見守った 1 回の実行、見積もり）では
`cache_read` / `cache_write` は一度も報告されませんでした: どの呼び出しも冷えたプロンプトでした。
W6-F（#640）: モデル呼び出しの最中に止まり、その呼び出しが終わった反復の行にも、その呼び出しの
`tokens_in` / `tokens_out` が入ります。

**起床の刻印（修正 1 回目）。** 押下は **起床の刻印**（`WakeStamp`）を運びます: 起床時に読んだ権限の
エポック、人のターンの数（反復の `seq0`）、グラントの停止エポック、スケジューラーの実行トークン（`stop`
の最初の瞬間に無効）とスイッチ。`step` はこれを受け入れの確認で（tick の条件と一緒に、プロバイダーを
読む前に）、その直後に（`fresh`: ハートビートを今読む）、**公開の権限フェンスの中で**
（`commit_at_epoch(expected=<起床のエポック>)` とメモリだけの印 — 反復の公開と 1 つの手順）、そして反復の
**最初の効果** の直前に（許可は起床のエポックのものでなければならず — `consume` がそのエポックがまだ
現在のものかを不可分に確かめる — 刻印もまだ新しいこと）確かめます。修正 2 回目で、刻印には取った
実行部も入り（1 回だけ使える）、記録全体（`fresh`）を **最初の許可** の直前、**最初の消費** の直前、
**最初のプロバイダー要求** の直前（グラントの確認も: ブレーカー・TTL・時計・状態）、**最初の末端要求**
（クライアントの代理の許可の手順）で読み直し、メモリの印（スイッチ・実行トークン・実行部・キル・人の
ターン・権限のエポック）は以降の **すべて** の境界で読みます。**保証すること:** これらの読み取りの時点で
起きている停止・縮小・一時停止と再開・キル・取り消し・ブレーカー・TTL の終わり・人のターン（来て去った
ものも）・スケジューラーの停止・実行部の差し替え・スイッチの変更、そして最初の要求の前の最後の読み取りで
見えているハートビートの喪失は拒否されます: 公開前なら見送り（`narrowed`、`turn_busy`、
`scheduler_stopped`、`executor_unavailable`、`heartbeat_unhealthy` …）、公開後ならプロバイダーへの要求も
書込みもないまま `permit_stale(tick_stale)` / `stopped(tick_stale)` で終わります。**受け入れた残り**
（親の決定、修正 2 回目）: ハートビートは外部の観測で、標本として読みます — 要求の前の最後の読み取りの
あと（HTTP 要求が出る直前の最後の命令の間）に起きた喪失はその要求には見えず、反復の最初の要求のあとの
ハートビートの喪失は停止になりません（メモリの印は停止になる。ハートビートは *開始* の条件、ADR 0021
§8）。同じ最後の窓でのスケジューラーの停止も、その 1 回の要求には見えません。実際の停止では実行部が
スケジューラーより先に止まるので、実行部自身の停止フラグで拒否されます。理由には `shutdown`（実行部が停止中。
イベントなし）と `repeated_failure`（最後の押下か再開以降、`failed` / `model_error` / `timeout` の終わりが
3 回続いた: 何もしない反復のゲートと同じく、人が押すか再開するまで）も加わりました。

**起動時に使えないとき。** スイッチがオンでもスケジューラーが動いていなければ、サーバーは構造化した
警告を 1 行 `grants: heartbeat_start unavailable (reason=scheduler_off)` 出し、ティッカーは作られても
何にもつながらず（起こされない）、フラグ付きのグラントの tick ブロックに `unavailable: scheduler_off` が
載ります。スケジューラーは動いていてもハート
ビートがオフ（または起動時に動いていない）なら `grants: heartbeat_start unavailable (reason=heartbeat_off)`
を出し、フラグ付きのグラントの tick ブロックに `unavailable: heartbeat_off` が載ります（どの起床も
`heartbeat_unhealthy` になる。ハートビートをオンにして再起動してください）。評価の失敗は種類ごとに
5 分に 1 回まで記録します（例外のクラス名だけ）。

**どこで見えるか。** 設定の欄のグラントのカード: 「ハートビート開始: オン · 開始 n 回 · 最低間隔」、
最後の確認、理由ごとの見送り、最後のハートビート反復のトークンと秒数。Stage のボード（アクティビティ
表示）: 同じものを反復数の下の行として（許可リストのコードと数だけ。読み上げなし。新しいタイマーなし
— アクティビティの 1 本のポーリング）。

**ここでしないこと**（意図的に）: グラントの総量と 1 tick の上限を超える日次などの予算プールは無し
（公開リリース後）、YOLO の二重の結び付けの消費も無し、モデルによる判定・確認も無し、
tick の記録の保存も無し（実モデルでのスモーク W6e はコードではなく人が見守った 1 回の実行:
[autonomy_ja](autonomy_ja.md#4-既知の制約)）。

## Stage のボード（W5b）

Stage のホワイトボードの稼働状況モードに、サーバーの起動後に発行された最新のグラントを表示だけで出す
（同じ `GET /api/activity` の `grant`。`autonomy.stage_c` がオフならキー自体が無く、グラントが無ければ `null`）。
見出しの状態、目標の状態、反復 n / 最大と実行中か、残り時間と残り予算（この反復のトークン / 1 回の上限）、
最後の終わり方（言葉で）、直近 5 反復（終わり方のコード・所要時間・実際に呼んだツール名）、承認待ちの案内（承認ウィンドウと
承認ページを指すだけでカードの中身は出さない）と「あなたの確認待ち」の案内（W6c: 申告の証跡つき。「反復 k/最大 で申告 ·
チェック · 作業ツリー · 進捗」、チェックの行、申告時のトークン / 残り時間、「<時刻> から」。チェックが不合格なら琥珀色と
言葉の「⚠」の行、閾値を過ぎたら「まだあなたを待っています」、確定の後は閲覧だけ）。**目標の文・パス・引数・カードの中身は
出さず、操作も無い**（取り消し・一時停止・確認・1 反復を実行はこの設定の欄のまま）。読むのは
`GrantService.board_view()` と `GoalIterationExecutor.board()`（メモリだけ。look も保存先の読み書きもせず、ロックも待たない。取れなければ `grant_busy`。既知のコードだけを通す）。
`autonomy.stage_c_exec` がオンなら、反復の開始でボードが閉じていれば稼働状況で下りてくる。判定表は
[stage.md](stage.md#the-goal-grant-on-the-board-adr-0011-stage-c-w5b-of-296)。
